4.1 Lecture - Real-Time Mode in Structured Streaming

The realTime trigger, supported sources, compute setup, and when to use it

Real-Time Mode is a Spark Structured Streaming feature, introduced with Spark 4 on Databricks, that swaps the default micro-batch execution for a continuous, always-on dataflow. It targets sub-second end-to-end latency for operational workloads reading from message buses. This lecture covers what it is, what it requires, what it supports, and when to choose it over the micro-batch patterns from sections 2 and 3.

Learning Objectives

By the end of this lecture, you will be able to:

  • Explain what the Real-Time trigger does and how it differs from processingTime and availableNow
  • Describe the message-bus sources and sinks that Real-Time Mode supports
  • Configure a classic compute cluster correctly for Real-Time Mode
  • Describe Real-Time Mode's update output mode and the operators that work with it
  • Interpret the RTM-specific latency metrics from StreamingQueryProgress
  • Match a workload to the right streaming pattern based on latency budget and source type

A. What Real-Time Mode Is

Spark Structured Streaming's default execution model is micro-batch: the engine slices the input into small batches on a fixed cadence (typically every few seconds) and runs each batch as an ordinary Spark job. End-to-end latency is bounded below by the trigger interval plus the batch's own runtime - usually 5-30 seconds.

Real-Time Mode replaces that with a long-running continuous query. Records flow through the operator graph as soon as they arrive - no batch boundary, no inter-batch latency. Target end-to-end latency is sub-second. The only code change is the trigger:

Micro-Batch Mode (default)
Records arrive
▼
Wait for trigger
(every 5-30s)
▼
Run as Spark job
▼
Write batch
Real-Time Mode (realTime trigger)
Records arrive
▼
Continuous query
(always running)
▼
Write per-record
# wakes up every 10s, processes whatever arrived
.trigger(processingTime="10 seconds")
# continuous dataflow, sub-second latency
.trigger(realTime="5 minutes")  # checkpoint cadence
The realTime interval is misleading

In .trigger(realTime="5 minutes"), the "5 minutes" is the checkpoint interval - how often Spark commits offset progress. It is not the processing latency, which targets sub-second. PySpark requires the interval to be specified; Scala can call RealTimeTrigger.apply() with no argument.

B. Supported Sources and Sinks

Real-Time Mode is built around message-bus connectors. The table below summarises the currently supported pairings.

Connector As source As sink
Apache KafkaYesYes
Event Hubs (Kafka connector)YesYes
Kinesis (EFO mode)Yes-
AWS MSKYes-
Arbitrary sinks (forEachWriter)n/aYes
Kafka in, Kafka or custom sink out

For the demo in 4.2 we read from a Confluent Cloud Kafka topic and write to an in-memory sink for live notebook visualization. In production the typical RTM pattern is Kafka -> RTM transform -> Kafka (or Event Hubs) for downstream consumers, or Kafka -> RTM -> forEachWriter for arbitrary sinks like alerting webhooks or cache updates. Note that file sources and UC tables are not RTM sources - those workloads stay on micro-batch.

C. Compute Prerequisites

Real-Time Mode is fussy about compute - more than any other Spark feature. The settings below are required; missing any one of them produces a query that runs but silently falls back to micro-batch behavior, or fails at start-up.

Cluster type: Classic compute

Dedicated (single-user) or Standard (shared) access mode. Serverless is not supported. Apache Spark™ Declarative Pipelines (classic or serverless) is also not supported.

DBR 16.4 LTS or above

Earlier runtimes do not have the Real-Time trigger. 18.2+ is recommended for low-throughput workloads using transformWithState.

Autoscaling: OFF

A continuous query holds task slots indefinitely. Autoscaling can't safely add or remove nodes under it.

Photon: OFF

Photon's vectorised execution batches rows internally - incompatible with the per-record continuous model.

Spot instances: OFF

Spot reclaims kill the long-running query. Use on-demand for any RTM cluster.

Spark conf flag

Set spark.databricks.streaming.realTimeMode.enabled = true on the cluster, in the Advanced -> Spark Config section.

Slot calculation

A continuous query holds all its task slots simultaneously. For a single-stage stateless Kafka pipeline you need at least one slot per Kafka partition (or per maxPartitions). Add stateful stages (shuffles) and the slot count grows fast - a Kafka source + one shuffle stage of 20 partitions needs 28 slots, not 20. Plan cluster size around the worst stage, not just the source.

D. Output Mode and Operator Support

Real-Time Mode supports update mode only. Append and complete output modes are not available. Most Structured Streaming operators are supported, with a few important exceptions.

Supported
  • Selection, projection, UDFs (Python and Scala)
  • Aggregations: sum, count, max, min, avg, others
  • Tumbling and sliding windows
  • dropDuplicates (state is unbounded - watch memory)
  • Broadcast (stream-to-table) joins on small tables
  • transformWithState (Row interface)
  • union, forEach
Not supported
  • Append and complete output modes
  • Session windows
  • dropDuplicatesWithinWatermark
  • Stream-to-stream joins
  • (flat)MapGroupsWithState, mapPartitions
  • forEachBatch
  • transformWithStateInPandas (use Row variant)
  • Python UDTFs and UC UDFs
Python UDF tuning

For minimum latency, set spark.sql.execution.arrow.maxRecordsPerBatch=1. This optimises for latency at the cost of throughput - the right default for most RTM workloads. Pandas UDFs perform poorly at batch size 1; prefer Arrow UDFs in RTM if you can. For latency-critical UDFs, prefer Dedicated access mode over Standard - shared-mode security isolation adds overhead.

E. Observability - RTM Latency Metrics

Real-Time Mode adds latency-specific fields to the streaming query progress events. They tell you whether a query is meeting its sub-second budget and where any bottleneck sits.

Metric What it measures Healthy value
processingLatencyMs Time spent inside Spark operators per record Single-digit ms for stateless
sourceQueuingLatencyMs Time records waited in the source connector before pickup Sub-second for a healthy Kafka source
e2eLatencyMs Source ingestion timestamp to sink commit Sub-second target

Inspect the metrics from a running query with lastProgress:

import json


# Inspect the metrics from a running query
print(json.dumps(query.lastProgress, indent=2))

Diagnosis pattern - high e2eLatencyMs with low processingLatencyMs usually means upstream queuing (Kafka lag, partition imbalance) or sink slowness, not a Spark problem. Conversely, high processingLatencyMs points at an expensive operator or shuffle.

F. Decision Framework - When to Use Each

Micro-batch and Real-Time Mode address different shapes of workload. Pick by latency budget, source type, and operational tolerance. Click each workload shape on the left to see the recommended pattern.

Files or Delta source, minutes OK Ingestion, ETL, bronze layers Kafka, sub-second processing Alerting, fraud, control loops Kafka, analytics + history Dashboards, BI, ML features Stateful: sessions, joins Sessionization, CEP
The summary

Micro-batch Structured Streaming is the right answer for most analytics workloads - file and Delta sources, stateful patterns, and anything where seconds-level freshness is acceptable. Real-Time Mode on Kafka is the right answer for sub-second operational use cases on a message-bus source. Pick the pattern that matches the workload's source type and latency budget.

G. Primer - The Demo Scenario

The demo in 4.2 reads a stream of synthetic stock-trade events from a Confluent Cloud Kafka topic and renders a live per-symbol price chart. The events come from Confluent Cloud's managed Sample Data Datagen Source connector - the Stock trades template - so there is no producer code to run. Stock trading is a good fit for a real-time demo because sub-second latency is genuinely meaningful: tick-by-tick prices, volume spikes and order flow all need continuous processing rather than micro-batched snapshots.

Trade event shape

Each Kafka message carries one trade: side (BUY/SELL), quantity, symbol, price, account, userid. Price is in 1/100 of a cent - divide by 10000 to get USD.

Streaming aggregate

The demo's RTM query computes per-symbol 30-second tumbling windows: trade count, average price, high/low, and total traded volume. Live chart auto-refreshes as new windows complete.

The Sample Data connector publishes a small set of fictional symbols (ZJZZT, ZVZZT, etc.) so there's no risk of confusing the demo data with real market data. Throughput is steady - enough to see the chart move within seconds of starting the streaming query.

Key Takeaways

  • Real-Time Mode swaps Spark's micro-batch execution for a continuous, always-on dataflow targeting sub-second end-to-end latency
  • Built around message-bus connectors - Kafka, Event Hubs, Kinesis (EFO), MSK - with Kafka, Event Hubs and forEachWriter available as sinks; file and Delta sources stay on micro-batch
  • Needs classic compute (DBR 16.4+) with autoscaling, Photon and spot all OFF, and spark.databricks.streaming.realTimeMode.enabled=true
  • Update mode only; most common operators supported - selection, projection, UDFs, aggregations, tumbling and sliding windows, dropDuplicates, broadcast joins, transformWithState (Row interface)
  • lastProgress exposes processingLatencyMs, sourceQueuingLatencyMs, and e2eLatencyMs for validating the sub-second budget
  • Use micro-batch triggers (processingTime, availableNow) for analytics and stateful patterns; use the realTime trigger for Kafka with sub-second processing
