Stream Processing and Analysis with Apache Spark | 1. Introduction to Stream Processing

1.1 Lecture - Introduction to Stream Processing

Processing data that never stops arriving

This lecture introduces the fundamentals of stream processing: what makes a data stream different from a batch, how Spark's streaming support evolved into Structured Streaming, how micro-batch execution works, and where stream processing is applied in the real world.

Learning Objectives

By the end of this lecture, you will be able to:

  • Describe basic stream processing concepts, including unbounded data sets
  • Explain the evolution from Spark Streaming (DStreams) to Structured Streaming
  • Describe how micro-batch execution processes a stream as a series of small batches
  • Identify common use cases for stream processing and the typical sources and destinations

A. What Is a Data Stream

A stream is an unbounded data set:

  • It has no theoretical beginning nor end - new records keep arriving for as long as the producing systems run
  • In contrast, a batch is of known, finite size at the time of processing
  • Streams can be messages from a messaging system such as Kafka; or
  • Streams can be anything event driven, such as files being processed as they arrive in cloud storage
Batch processing
  • Input is complete before processing starts
  • Results are computed once over the whole data set
  • Latency measured in minutes to hours
  • Examples: nightly ETL, monthly reporting
Stream processing
  • Input is unbounded - it never finishes arriving
  • Results are updated continuously or incrementally
  • Latency measured in milliseconds to minutes
  • Examples: fraud detection, live dashboards
ℹ️
Not All Streaming Is Real-Time

Stream processing is about how data is processed (incrementally, as it arrives), not necessarily how fast. Many production streaming pipelines run on minute-level or even hourly cadences - the incremental processing model is what saves recomputing everything. Real-time (sub-second) processing is a specific subset, covered in section 4.

B. From DStreams to Structured Streaming

Spark's streaming support has evolved through three generations:

  • Spark Streaming (2013) was introduced as an extension to core Spark
    • Built on the RDD API
    • Used the DStream (Discretized Streams) model: the stream as a sequence of time-windowed RDDs
    • Processed data in small time-based batches
  • Structured Streaming (2016) replaced DStreams
    • Built on the DataFrame and Dataset APIs
    • Introduced event-time processing
    • Simplified API with SQL-like operations
    • Better handling of late and out-of-order data
  • Spark 4 (current) continues to build on Structured Streaming
    • transformWithState: a new arbitrary stateful processing API
    • The state store data source, for querying streaming state directly when debugging
    • On Databricks, Real-Time Mode: a continuous execution mode targeting sub-second latency (section 4)
⚠️
DStreams Are Legacy

The DStream API is legacy and receives no new features. All new streaming development should use Structured Streaming, which is the only streaming API covered in this course.

C. Micro-Batch Execution

Micro-batching is the basis for stream processing in a distributed environment:

  • Micro-batching processes a stream as a series of small batches
  • Data is collected into time-based chunks
  • Each chunk is processed as a mini batch job using the same engine that runs batch workloads
  • Typical batch intervals range from around 100 milliseconds to a few seconds
  • The same fault tolerance, optimization, and scaling machinery as batch Spark applies to every micro-batch

D. Streaming in the Real World

Where stream processing earns its keep:

💡 Streaming use cases
  • Fraud detection
  • Live dashboards
  • Anomaly detection
  • Clickstream analysis
  • Sensor and IoT monitoring
  • Continuous data ingestion and transformation
🔌 Common sources and destinations
  • Apache Kafka
  • Amazon Kinesis
  • Azure Event Hubs
  • Cloud storage file arrivals
  • Alerts and notifications (destination)
  • Lakehouse tables - Delta Lake, Apache Iceberg (destination)

A single pipeline often combines several of these: for example, clickstream events land in Kafka, Spark aggregates them incrementally, and the results feed both a UC table for analytics and an alerting destination for operations.

Summary

  • A stream is an unbounded data set: it has no defined end, in contrast to a batch of known size
  • Spark Streaming (DStreams, RDD-based) gave way to Structured Streaming (DataFrame-based, event-time aware) in 2016; Spark 4 adds transformWithState, the state store data source, and (on Databricks) Real-Time Mode
  • Micro-batch execution processes the stream as a series of small batch jobs, reusing Spark's batch engine, fault tolerance, and optimizations
  • Streaming powers fraud detection, dashboards, anomaly detection, clickstream analysis, and IoT monitoring, typically reading from message buses or file arrivals and writing to lakehouse tables or alerting systems
  • Stream processing is about incremental processing, not necessarily sub-second latency
