2.1 Lecture - Spark Structured Streaming

A declarative API for distributed stream processing

This lecture covers the Spark Structured Streaming API: the infinite table model, streaming sources and sinks, the DataStreamReader and DataStreamWriter interfaces, streaming transformations and queries, and the controls that shape query behavior - triggers, output modes, checkpointing, and monitoring.

Learning Objectives

By the end of this lecture, you will be able to:

  • Explain how streaming data is processed through micro-batching in Spark
  • Work with streaming sources and sinks to read and write data
  • Describe how transformations and streaming queries work with streaming DataFrames
  • Manage streaming applications using triggers, output modes, checkpointing, and monitoring

A. The Infinite Table Model

Structured Streaming treats streaming data as an infinite table:

  • Each new record is a row appended to the input table
  • Queries are continuously and incrementally updated as new data arrives
  • The same DataFrame APIs as batch processing apply - write the query as if the data were static
  • Query plans are automatically optimized by the same Catalyst optimizer as batch
  • Key features:
    • Event-time processing
    • Watermark support for late data (section 3)
    • End-to-end exactly-once guarantees with replayable sources and idempotent sinks
▶ New records become rows appended to an unbounded input table

B. Streaming Sources and Sinks

Where your streaming data comes from - the built-in sources:

Source Description
File Reads files from a directory as they appear
Kafka Reads data from Apache Kafka topics
Delta Reads a UC table as a stream of changes
Socket Reads data from a socket connection (for testing)
Rate Testing source that generates data at a fixed rate

And where it goes - the built-in sinks:

Sink Description
File Stores the output to a directory
Kafka Writes output to Kafka topics
Delta Writes output to UC tables (the standard sink on Databricks)
Foreach / ForeachBatch Runs arbitrary computation on the output records
Console / Memory Used for testing and debugging
ℹ️
Auto Loader

On Databricks, Auto Loader (cloudFiles) is an enhanced file source for high-performance cloud storage ingestion with automatic schema inference and evolution. This course uses the standard file source to keep the focus on the core API; Auto Loader is a drop-in upgrade for production ingestion.

C. DataStreamReader and DataStreamWriter

Two interfaces bracket every streaming pipeline:

  • DataStreamReader: creates streaming DataFrames - accessed through spark.readStream
  • DataStreamWriter: writes streaming results - accessed through DataFrame.writeStream
# Create a streaming DataFrame from JSON files in a directory
stream_df = (
    spark.readStream
    .format("json")
    .schema(order_schema)              # file sources require an explicit schema
    .option("maxFilesPerTrigger", 1)   # throttle: one file per micro-batch
    .load("/Volumes/catalog/schema/volume/orders")
)


# Write streaming results to a UC table
query = (
    stream_df.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", checkpoint_path)
    .toTable("orders_bronze")
)
⚠️
Schemas Are Not Inferred on File Streams

Unlike batch reads, streaming file sources require the schema up front - inferring it would mean scanning an unbounded source. Define a StructType (or use Auto Loader's schema inference, which manages this for you).

D. Streaming Transformations and Queries

Between the reader and the writer sits ordinary DataFrame code:

# Transformations: identical to batch DataFrame code, still lazy
from pyspark.sql.functions import col


large_orders_df = (
    stream_df
    .filter(col("quantity") >= 24)
    .withColumn("is_bulk", col("quantity") >= 48)
)


# The streaming query: starts execution and runs until stopped
query = (
    large_orders_df.writeStream
    .outputMode("append")
    .format("delta")
    .queryName("large_orders")
    .trigger(processingTime="1 second")
    .option("checkpointLocation", checkpoint_path)
    .toTable("large_orders")
)


# Manage the query lifecycle
query.stop()               # stop on request
query.awaitTermination()   # block until the query terminates
  • Transformations on a streaming DataFrame produce new streaming DataFrames - nothing executes until a query starts
  • start() (or toTable()) launches a StreamingQuery that runs indefinitely until stopped or failed
  • queryName() labels the query in the Spark UI and names the temp view for memory sinks

E. Triggers

Triggers control when Structured Streaming processes data:

  • Default trigger (as soon as possible)
    • Processes data as soon as the previous micro-batch completes
  • Fixed interval trigger (processingTime)
    • Processes data at specified time intervals
    • Useful for controlling resource usage
  • Available now trigger (availableNow)
    • Processes all available data (in multiple batches if throttled), then stops
    • Will not wait for new data to arrive afterwards - ideal for incremental batch jobs and for classroom demos
# Default when no trigger is specified
df.writeStream.start()


# Process batches at fixed intervals
df.writeStream.trigger(processingTime="2 minutes").start()


# One-time processing of available data, then stop
df.writeStream.trigger(availableNow=True).start()
💡
A Fourth Trigger in Spark 4

On Databricks with Spark 4, the realTime trigger enables Real-Time Mode - continuous execution targeting sub-second latency. It has its own compute requirements and constraints, covered in section 4.

F. Output Modes

Output modes define how Structured Streaming writes results to sinks:

  • append (default)
    • Only adds new records to the sink
    • Best for simple (or stateless) queries without aggregations
  • update (ideal for dashboards and real-time metrics)
    • Modifies existing records and adds new ones
    • Only outputs records that changed since the last trigger
  • complete (ideal for running totals or leaderboards)
    • Writes the entire result table to the sink each time
    • Required for some aggregations
ℹ️
Mode and Query Shape Must Agree

Not every mode works with every query. A stateless projection cannot run in complete mode (there is no result table to re-emit), and an aggregation without a watermark cannot run in append mode (rows are never final). Spark validates the combination when the query starts.

G. Checkpointing and Fault Tolerance

The checkpoint location is the durable memory of a streaming query:

  • Records which input has been processed (source offsets) and any operator state
  • Enables recovery: restart the query with the same checkpoint and it resumes exactly where it left off
  • Enables exactly-once end-to-end guarantees when combined with replayable sources (files, Kafka, Delta) and idempotent sinks (Delta)
  • One checkpoint location per query - never share one between queries
query = (
    df.writeStream
    .option("checkpointLocation", "/Volumes/catalog/schema/checkpoints/orders_bronze")
    .toTable("orders_bronze")
)

H. Monitoring Streaming Queries

Understanding your streaming application's health:

  • Spark UI: the Structured Streaming tab shows active queries with per-batch progress details
  • External monitoring tools: Datadog, Grafana, Prometheus, and similar can track processing rates, latency, memory usage, and garbage collection
  • Inspection from code:
# Check if a DataFrame is streaming
df.isStreaming            # returns True or False


# Get the unique identifier for a query
query.id


# Get the current state of a query
query.status


# Inspect the most recent progress report (rates, durations, offsets)
query.lastProgress


# List all active queries on the session
spark.streams.active

Summary

  • Structured Streaming models a stream as an infinite table: new records are appended rows, and your DataFrame query is incrementally recomputed against them
  • spark.readStream builds streaming DataFrames from sources (file, Kafka, Delta, rate); DataFrame.writeStream writes to sinks (Delta, file, Kafka, memory, console, foreach)
  • Transformations are the same lazy DataFrame operations as batch; start() or toTable() launches a streaming query that runs until stopped
  • Triggers control when processing happens (processingTime, availableNow, default as-fast-as-possible); output modes control what is written (append, update, complete)
  • Checkpoint locations record offsets and state, enabling restart recovery and exactly-once guarantees with replayable sources and idempotent sinks
  • Monitor queries via the Spark UI, external tools, and query.status / query.lastProgress
