3.1 Lecture - Stream Aggregations, Windows and Watermarks

Stateful stream processing: aggregating data that never stops

This lecture covers advanced stream processing and analysis: the difference between stateless and stateful operations, how state is maintained in a distributed streaming application, streaming aggregations, the window types used for time-based computations, watermarks for late data, and streaming joins.

Learning Objectives

By the end of this lecture, you will be able to:

  • Describe the key differences between stateful and stateless streaming operations
  • Explain how and why state is maintained and managed in distributed streaming applications
  • Describe streaming joins, their supported types, and their limitations
  • Apply the different window types (tumbling, sliding, and session) for time-based computations and handle out-of-order events using watermarks

A. Stateful vs Stateless Operations

Understanding how streaming operations handle data over time:

  • Stateless operations
    • Process each record independently
    • No memory of previous records
    • Examples: select, filter, withColumn
  • Stateful operations
    • Maintain information across micro-batches
    • Require a checkpoint location
    • Examples: groupBy, join, dropDuplicates, and window operations (covered below)
ℹ️
Why the Checkpoint Location Matters for State

The checkpoint location is needed to: (1) maintain state across batches, (2) recover state in case of failures, and (3) handle replay of data without duplicating results.

B. Maintaining State

Managing state in distributed streaming applications:

  • Challenges in distributed state
    • Data is distributed across worker nodes
    • State must be fault tolerant to survive node failures
    • Memory is limited relative to potentially large state
    • Consistency must hold across failures and restarts
  • RocksDB as the state store
    • Built-in state store backend for Spark Structured Streaming
    • Persists state off-heap with high performance
    • Features: efficient storage and retrieval, automatic compaction, support for large state sizes
💡
Spark 4: Inspecting State Directly

Spark 4 adds the state store data source, which lets you read a query's state as a DataFrame (spark.read.format("statestore").load(checkpoint_path)) - invaluable when debugging why a stateful query holds more state than expected.

C. Streaming Aggregations

Understanding aggregations in streaming applications:

  • Types of streaming aggregations (typically operating on grouped data):
    • count
    • sum / avg
    • min / max
  • Approximate functions are available which typically perform better, e.g. approx_count_distinct()
❓
How Can We Aggregate an Incomplete Data Set?

Recall that streaming DataFrames are unbounded. A plain groupBy().count() over an unbounded stream is a running total whose state grows forever - every group ever seen stays in the state store. The answer for time-series analysis is to aggregate based upon windows: bounded slices of event time whose state can eventually be finalized and dropped.

D. Window Operations

Windowing scopes a streaming computation to slices of time:

  • Tumbling windows: fixed, non-overlapping intervals (e.g. count events every 5 minutes)
  • Sliding windows: overlapping windows where an event can belong to multiple windows
  • Session windows: dynamically sized windows based on activity, closing after a gap or session timeout

Windows are expressed with the window() function inside groupBy(), operating on an event-time column - the time the event occurred, not the time Spark processed it.

Sliding Window Example

Get the number of credit card authorizations for the last 60 seconds, every 30 seconds:

from pyspark.sql.functions import window, count


authorizations = ...  # Schema: { timestamp: Timestamp, card_id: String, amount: Double }


windowed_auths = (
    authorizations
    .groupBy(
        window(
            timeColumn=authorizations.timestamp,   # the event-time column
            windowDuration="60 seconds",           # each window covers 60 seconds
            slideDuration="30 seconds"             # a new window starts every 30 seconds
        ),
        authorizations.card_id                     # additional grouping key
    )
    .agg(count("*").alias("transaction_count"))
)


# Start a streaming query to send the output to a sink

Omit slideDuration and the same call produces tumbling windows. The result includes a window struct column with start and end fields.

E. Handling Late Arriving Data

Events can be delayed in arriving for many reasons - network partitions, device buffering, upstream retries. A delayed event may carry a timestamp for a window that has already been processed.

Watermarks define how long Spark waits for out-of-order events:

windowed_auths = (
    authorizations
    .withWatermark("timestamp", "2 minutes")   # accept events up to 2 minutes late
    .groupBy(
        window(authorizations.timestamp, "60 seconds", "30 seconds"),
        authorizations.card_id
    )
    .agg(count("*").alias("transaction_count"))
)
  • Events arriving within the watermark threshold are incorporated into their (late) windows
  • Events arriving beyond the threshold may be dropped
  • Crucially, the watermark lets Spark finalize and drop old window state, preventing unbounded state growth
  • A watermark is required to use append output mode with aggregations, since it defines when a window's result is final
💡
Choosing a Threshold

The watermark threshold is a trade-off: longer thresholds tolerate later data but hold more state and delay finalized results; shorter thresholds finalize quickly but drop more late events. Base it on the actual lateness distribution of your source.

F. Streaming Joins

Understanding join types and limitations in streaming applications:

  • A streaming DataFrame can be joined with:
    • Another streaming DataFrame (stream-stream join)
    • A static DataFrame (stream-static join), including a normal DataFrame or the results of a complete output mode streaming operation
  • All join types are supported except full outer and cross joins (support varies by combination)
  • Challenges and limitations:
    • Stream-stream joins require maintaining state, increasing memory usage
    • Events from both streams must arrive within a defined interval to match
    • Late arriving data can present challenges - watermarks on both sides bound the join state
# Stream-static join: enrich a stream with reference data (no special handling)
enriched = orders_stream.join(customers_static_df, "customer_id")


# Stream-stream join: watermark both sides and bound the match interval
joined = (
    orders_stream.withWatermark("order_time", "10 minutes")
    .join(
        payments_stream.withWatermark("payment_time", "10 minutes"),
        expr("""
            orders.order_id = payments.order_id AND
            payment_time BETWEEN order_time AND order_time + INTERVAL 10 MINUTES
        """)
    )
)

Summary

  • Stateless operations (select, filter) process each record independently; stateful operations (groupBy, join, dropDuplicates, windows) maintain state across micro-batches and require a checkpoint location
  • RocksDB is the built-in state store backend, providing persistent, high-performance state at scale; Spark 4's state store data source lets you query that state directly
  • Plain aggregations over an unbounded stream accumulate state forever - window operations bound aggregations to slices of event time
  • Tumbling windows partition time into fixed non-overlapping intervals; sliding windows overlap; session windows size themselves around activity gaps
  • Watermarks define how long to wait for late events, allowing Spark to finalize windows and drop old state
  • Stream-static joins are straightforward enrichment; stream-stream joins need watermarks on both sides and a bounded match interval to keep state in check
