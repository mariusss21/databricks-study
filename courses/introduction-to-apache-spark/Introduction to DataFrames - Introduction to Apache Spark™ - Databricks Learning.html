2.1 Lecture - Introduction to DataFrames

Structured data processing in Apache Spark

This lecture introduces the DataFrame, the primary data abstraction in modern Spark, and explains how DataFrame operations are lazily evaluated and optimized before they run.

Learning Objectives

By the end of this lecture, you will be able to:

  • Describe the DataFrame abstraction, including schema enforcement and distributed storage
  • Distinguish transformations from actions and explain lazy evaluation
  • Describe how the Catalyst optimizer and Photon engine optimize DataFrame execution
  • Explain why columnar storage suits analytical workloads

A. What is a DataFrame?

DataFrames are distributed collections of records, all with the same pre-defined structure (schema):

  • Built on Spark's core concepts but with structure, optimization, and familiar SQL-like operations for data manipulation
  • DataFrames track their schema and provide native support for many common SQL functions and relational operators (JOIN, GROUP BY, and so on)
  • DataFrames are evaluated as DAGs, using lazy evaluation, and carry lineage information that provides fault tolerance
  • A DataFrame looks like a single table to you, but its rows are physically split into partitions spread across the Executors of the cluster
▶ One logical table, many physical partitions

B. Creating DataFrames

DataFrames can be created from:

  • JSON, CSV, Parquet, ORC, text, or binary files
  • Delta Lake or other table storage format directories
  • A table or view in a catalog (like Unity Catalog)
  • An external database
  • An existing RDD (classic compute only)
# From a file
df = spark.read.csv("/Volumes/my_catalog/my_schema/files/people.csv")

# From a table
df = spark.read.table("my_catalog.my_schema.people")

# From a range of numbers
df = spark.range(1000)

C. Transformations and Actions

DataFrames are immutable - once created, their data cannot be modified. Instead:

  • Transformations create new DataFrames from existing ones; they describe what to compute, not when
  • Actions (like counting, showing, or saving output) trigger actual computation and produce final results

Multiple transformations can be chained; the job is only created when an action is requested - a process called lazy evaluation.

▶ Lazy evaluation: transformations build a plan, actions run it

▶ Expand for More Details
Why Lazy Evaluation Matters
  • Because Spark sees the whole chain of transformations before anything runs, the optimizer can rearrange, combine, and prune work - for example pushing a filter down to the file scan so less data is read in the first place.
  • Lineage (the recorded chain of transformations) is also what makes DataFrames fault tolerant: a lost partition can be recomputed by replaying its lineage.
  • A common surprise for new users: defining ten transformations takes milliseconds and runs nothing. The cost is paid when an action such as count(), display(), or write executes the accumulated plan.

Common DataFrame API Methods

The most frequently used transformations:

Transformation Description
__select()__ Choose specific columns from a DataFrame
__filter()__ Filter rows based on a condition, alias where()
__withColumn()__ Add or modify a column in a DataFrame
__groupBy()__ Group rows in a DataFrame by specified columns
__agg()__ Aggregate rows in a DataFrame after grouping

And the most frequently used actions, which trigger execution:

Action Description
__count()__ Return the number of rows in a DataFrame
__show()__ Display DataFrame contents
__take(n)__ Return the first n rows from a DataFrame
__first()__ Return the first row from a DataFrame
__write__ Save a DataFrame to storage

For more information see the DataFrame API reference.

D. DataFrame API Optimizations

Because DataFrame operations are declarative, Spark is free to optimize how they execute:

  • Adaptive Query Execution (AQE) - dynamic plan adjustments (cost-based optimization) during runtime based on actual data characteristics and execution patterns
  • In-Memory Columnar Storage - an in-memory columnar format for DataFrames enabling efficient analytical query performance and a reduced memory footprint
  • Built-in Statistics - automatic statistics collection when saving to optimized formats (Parquet, Delta) enables smarter query planning and execution
  • Catalyst Optimizer and Photon - discussed below

E. DataFrame (or Query) Planning

When a DataFrame is evaluated, the Driver creates an optimized execution plan through a series of transformations - converting the logical plan into an efficient physical execution plan that minimizes resource usage and execution time.

▶ Expand for More Details
The Planning Phases
  • Analysis resolves names against the catalog: which table does customers refer to, what type is account_balance, does the referenced column exist?
  • Logical optimization applies rule-based rewrites such as predicate pushdown (filter as early as possible), column pruning (read only the columns used), and constant folding.
  • Physical planning selects concrete execution strategies - for example choosing a broadcast join over a shuffle join when one side is small.
  • Code generation compiles the chosen plan into efficient JVM bytecode (or hands it to Photon for vectorized native execution on Databricks).
  • You can inspect the plans for any DataFrame with df.explain() - the ETL demo in Section 4 does exactly this.

Catalyst Optimizer and Photon

Catalyst Optimizer:

  • The query optimization engine that converts DataFrame operations into an optimized execution plan
  • Applies rule-based and cost-based optimizations to improve query performance

Photon Engine:

  • The Databricks-native vectorized query engine that accelerates query execution
  • Processes data in batches rather than row-by-row for better performance
  • Runs by default on Databricks SQL warehouses and serverless compute
  • Can be enabled on All-Purpose and Job Clusters in Databricks

F. More on Columnar Storage

Columnar storage organizes data by column rather than by row, enabling efficient scanning and analysis. It is particularly efficient for analytical workloads and is implemented both in the DataFrame internal storage format and in physical file formats such as Parquet and ORC.

In row-oriented storage, all the values of a record are stored together. Reading one column means reading every row in full:

id: 1name: Adaamt: 100
id: 2name: Benamt: 250
id: 3name: Cyamt: 75

In column-oriented storage, all the values of a column are stored together. A query that sums amt touches only the last block, skipping the rest entirely:

id: 1id: 2id: 3
name: Adaname: Benname: Cy
amt: 100amt: 250amt: 75

Columnar layouts also compress better, because values within a column are of the same type and often similar.

Summary

  • DataFrames are distributed, immutable collections of records with a schema
  • Transformations describe work lazily; actions trigger execution of the accumulated plan
  • The Catalyst optimizer turns your code into an optimized physical plan; Photon accelerates execution on Databricks
  • Columnar storage (in memory and in formats like Parquet) makes analytical scans and aggregations efficient
