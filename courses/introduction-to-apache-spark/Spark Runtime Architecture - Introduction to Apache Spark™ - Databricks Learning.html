1.2 Lecture - Spark Runtime Architecture

How Spark plans, distributes, and monitors work across a cluster

This lecture examines the components of a running Spark application - the Driver, Cluster Manager, Workers, and Executors - and how Spark breaks work into jobs, stages, and tasks that you can observe in the Spark UI.

Learning Objectives

By the end of this lecture, you will be able to:

  • Identify the roles of the Driver, Workers, and Executors in Spark applications
  • Explain how the SparkSession serves as the unified entry point for Spark applications
  • Describe how a Spark application is decomposed into jobs, stages, and tasks
  • Use the Spark UI to monitor application progress, DAG visualizations, and resource allocation

A. The Runtime Architecture at a Glance

A Spark application is a coordinated set of processes. The Driver plans the work, the Cluster Manager allocates resources, and Executors on Worker nodes do the computation. Click the bar below to reveal the diagram.

▶ Spark runtime architecture diagram

The four roles:

  • Driver - the brain of a Spark application, responsible for planning and coordinating execution
  • Cluster Manager (Master) - manages cluster resources and allocates them to the Driver
  • Workers - nodes in the cluster that host Executors
  • Executors - processes on Worker nodes that execute tasks assigned by the Driver
▶ Expand for More Details
How the Pieces Interact
  • The client (a notebook, a job, or an application) submits work to the Driver. The Driver negotiates with the Cluster Manager for Executor resources, then communicates directly with those Executors to schedule tasks and collect results - shown as the dashed lines in the diagram.
  • Each Executor holds a cache, a region of memory for partitions you explicitly persist. Cached partitions can be reused across jobs without recomputation.
  • In Databricks, the Cluster Manager role is handled by the platform itself: when you create a cluster, Databricks provisions a Driver node and Worker nodes and wires them together for you.
Spark Connect: a Thinner Client
  • Spark 4 promotes Spark Connect, a client-server protocol in which your application holds only a lightweight client; the Driver runs remotely and receives query plans over gRPC.
  • This is how Databricks Serverless compute and Databricks Connect work: your notebook or IDE is the thin client, and the heavy lifting happens on the server side. The DataFrame code you write is identical either way.

B. The Spark Driver

The Driver plans, coordinates, and manages task execution. It:

  • Creates the SparkSession, the entry point for all Spark applications
  • Analyzes the Spark application and constructs a Directed Acyclic Graph (DAG)
  • Schedules and distributes tasks to Executors for execution
  • Monitors the progress of tasks and handles failures
  • Returns results to the client

C. The SparkSession

Introduced in Spark 2.0 as the unified entry point for all Spark functionality, replacing the separate SparkContext, SQLContext, HiveContext, and StreamingContext objects that earlier versions required.

from pyspark.sql import SparkSession
spark = (SparkSession.builder
    .appName("MySparkApplication")
    .config("spark.some.config.option", "some-value")
    .getOrCreate())
💡
Already Created in Databricks

In Databricks notebooks the SparkSession is created for you automatically and made available as the variable spark. You will almost never construct one yourself.

D. Executors

Executors are the processes that do the actual work:

  • Run on Worker nodes in a Spark cluster and host Tasks (for I/O and data processing)
  • Typically each Worker node runs one Executor, which has its own:
    • RAM cache
    • Disk cache
    • CPU cores
  • Interact with the Driver for task coordination and data transfer

E. The Spark DAG

Spark represents each job as a Directed Acyclic Graph of stages:

  • Spark jobs are broken down into Stages - groups of tasks that can be executed in parallel
  • Computations flow in one direction through the stages (the Directed bit)
  • Stages never loop back, ensuring the job terminates (the Acyclic bit)
  • Stages are organized into a dependency graph for execution flow (the Graph bit)

Why Stages Exist
  • Operations that can be applied to each partition independently (filter, project) are pipelined together into a single stage and execute in parallel across partitions.
  • A stage boundary appears wherever data must be redistributed across the cluster - the shuffle. Aggregating by key requires all rows for a key to be on the same Executor, so a new stage begins after the exchange.
  • In the Spark UI you will see this DAG rendered for every job, with each stage's operators and the dependencies between stages. Section 3 examines the shuffle in depth.

F. Spark Application Execution

A Spark application decomposes into a hierarchy: an application runs one or more jobs, each job consists of one or more stages, and each stage executes many tasks in parallel.

▶ Application, job, stage, and task hierarchy
📝
Shared Nothing

Tasks within a stage run in parallel and do not communicate with each other - a model known as shared nothing execution. One task processes one partition of data.

G. The Spark UI

Spark provides web user interfaces for monitoring and management, including:

  • Application UI - per application (one per SparkSession)
    • Application progress and task execution
    • DAG visualization and stage details
    • Resource usage and performance metrics
  • Master UI - per cluster
    • Worker node status, health, and cluster-wide resource allocation
    • Shows all running applications and available resources

In Databricks, the Spark UI is available from the cluster page (Compute -> your cluster -> Spark UI) and from the View links that appear under each executed notebook cell. The demo that follows explores the Jobs, Executors, and Storage tabs.

H. Spark Clusters in Databricks

The Databricks platform offers several options for running Spark workloads:

Compute Type Description
All-Purpose Clusters Interactive clusters that support notebooks, jobs, and dashboards with configurable auto-termination
Job Clusters Ephemeral clusters that start when a job runs and terminate automatically upon completion, optimized for non-interactive workloads
SQL Warehouses Optimized compute for SQL query performance with fast startup and auto-scaling to balance cost and performance
Serverless Fully managed compute where Databricks operates the cluster; your notebook connects as a thin client via Spark Connect

Summary

  • The Driver plans and coordinates; the Cluster Manager allocates resources; Executors on Workers run tasks
  • The SparkSession (available as spark in Databricks) is the unified entry point for all Spark functionality
  • Applications decompose into jobs, jobs into stages, and stages into parallel shared-nothing tasks
  • Stage boundaries occur at shuffles, where data is redistributed across the cluster
  • The Spark UI visualizes jobs, stages, the DAG, executors, and cached data
