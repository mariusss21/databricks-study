3.1 Lecture - Distributed Systems Programming Fundamentals

How Spark divides data and moves it between machines

This lecture covers the distributed systems concepts behind Spark's execution model. Understanding partitioning and the shuffle explains both why Spark scales and where its costs come from.

Learning Objectives

By the end of this lecture, you will be able to:

  • Describe core distributed system concepts including shared-nothing architecture, partitioning, and parallel processing
  • Explain how data moves between nodes in distributed operations, particularly during shuffle operations like groupBy and join
  • Describe the MapReduce algorithm for parallel data processing and its application in the DataFrame API

A. Shared Nothing Architecture

Spark follows the shared nothing model of distributed computing: nodes cooperate on a job without sharing memory or disk.

Independence
Each node works independently and manages its own resources (CPU, memory, disk).
Scalability
Adding more nodes can improve performance without resource contention.
Fault Tolerance
Failures are isolated to individual nodes, minimizing system-wide impacts.
Resource Partitioning
Data and workloads are partitioned across nodes to eliminate contention.

B. Partitioning

Partitioning is how Spark distributes data across the cluster.

Data distribution:

  • Data is divided into mutually exclusive in-memory partitions
  • Default partitioning is based upon the input and can be manipulated
  • The size and number of partitions affect parallelism

Processing model:

  • Each partition is processed independently
  • Multiple partitions can run in parallel
  • One partition = one task in Spark
  • Partitioning impacts performance and shuffle operations

C. The Shuffle Operation

The shuffle is how data moves between partitions in distributed processing.

What is shuffling?

  • Redistributing data across partitions
  • Required for operations like groupBy and join
  • The most expensive operation in Spark - it involves serializing data and moving it over the network

When it occurs:

  • Wide transformations (where output partitions depend on many input partitions)
  • Key-based operations
  • Data repartitioning
▶ All-to-all data movement between stages

▶ Expand for More Details
Why the Shuffle is Expensive
  • Every map-side partition may hold rows for every key, so each reduce-side partition must collect data from all map-side partitions - an all-to-all exchange across the network.
  • Shuffled data is serialized, written to disk on the map side, transferred, and deserialized on the reduce side. This is why a stage boundary appears at every shuffle in the DAG.
  • Minimizing shuffles - by filtering early and aggregating as late as possible with as little data as possible - is the single most effective Spark performance habit.
Adaptive Query Execution Helps
  • Since Spark 3 (and on by default in Spark 4), Adaptive Query Execution inspects the actual shuffle output at runtime and coalesces small shuffle partitions, picks better join strategies, and rebalances skewed partitions automatically.

D. MapReduce in Action

MapReduce is the classic pattern for parallel data processing, and it is exactly what a DataFrame pipeline compiles down to. Consider this small ETL job, which reads sales records, filters them, and totals the amount per id:

# READ: scan the source file into a DataFrame
input_df = spark.read.csv("sales_data.csv")

# MAP: narrow, per-partition transformations - no data movement
filtered_df = input_df.select("id", "amt").filter("amt > 50")

# SHUFFLE: groupBy sets the key, so all rows for the same id must be
# moved onto the same partition (the exchange) before aggregation
grouped_df = filtered_df.groupBy("id")

# REDUCE: aggregate each group after the shuffle - sum amt per id
aggregated_df = grouped_df.agg({"amt": "sum"})

# WRITE: each partition writes its slice of the result
aggregated_df.write.csv("/Volumes/catalog/schema/output/sales_by_id")

▶ Expand for More Details
Map Stage
  • Each input file becomes a partition, and the projection (select) and filter are applied to each partition independently - no data movement is required, so these are narrow transformations pipelined into one stage.
  • Note how B,30 and D,50 disappear at this stage: they fail the amt > 50 filter. Filtering early shrinks everything downstream, including the expensive shuffle.
Shuffle
  • groupBy('id') requires all rows with the same id to be in the same partition, so Spark redistributes the four map-side partitions into reduce-side partitions by hashing the key.
Reduce Stage
  • With each key's rows co-located, the sum is computed per key, and each reduce partition writes its own output file - which is why the result is a directory containing part-00000.csv and part-00001.csv rather than a single file.

E. Spark's Implementation

MapReduce sits at the core of everything Spark does.

Fundamental pattern:

  • Every Spark operation maps to Map / Shuffle / Reduce
  • Even simple transformations follow this model
  • It is the core building block for all distributed operations

Common examples:

Operation Map Shuffle Reduce
__groupBy__ Extract keys Redistribute by key Aggregate
__join__ Prepare keys Co-locate matching keys Combine rows
__filter__ Evaluate condition Not required Not required

Summary

  • Spark uses shared-nothing execution: independent nodes process mutually exclusive partitions in parallel
  • One partition = one task; partition count and size determine parallelism
  • The shuffle redistributes data by key between stages and is the most expensive operation in Spark
  • Every DataFrame pipeline compiles down to the MapReduce pattern: narrow transformations pipeline within a stage, wide transformations create shuffle boundaries
