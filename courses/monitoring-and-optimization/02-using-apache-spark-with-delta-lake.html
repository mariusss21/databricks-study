2.1 Lecture - Using Apache Spark with Delta Lake

ACID transactions, versioning, and maintenance for the tables your Spark workloads live on

This lecture covers Delta Lake: how its transaction log brings ACID guarantees to cloud storage, the operations it unlocks, and the maintenance and layout features - OPTIMIZE, VACUUM, and liquid clustering - that keep your tables fast.

Learning Objectives

By the end of this lecture, you will be able to:

  • Describe Delta Lake's architecture, including its transaction log, versioning system, and ACID properties on cloud storage
  • Apply key Delta Lake operations including MERGE, schema evolution, and time travel
  • Maintain and optimize UC tables with OPTIMIZE, VACUUM, and liquid clustering
  • Read from and write to UC tables using both Spark SQL and the DataFrame API
  • Position Apache Iceberg and UniForm in the open table format landscape

A. Introduction to Tabular Storage

Why open table formats exist: traditional data lakes have well-known problems.

  • No transactional guarantees: failed jobs leave partial data behind
  • No schema enforcement: bad records corrupt downstream pipelines
  • Performance issues with many small files
  • No built-in data quality controls
  • Difficult metadata management at scale
▶ Evolution of storage formats for cloud data lakes

B. Introduction to Delta Lake

An open format bringing ACID transactions to the data lake.

WHAT IS DELTA LAKE
  • Open source storage framework
  • Created by Databricks
  • Built on top of Parquet
  • Native Apache Spark integration
  • The default format on Databricks
KEY FEATURES
  • ACID transactions at scale
  • Schema enforcement and evolution
  • Time travel (data versioning)
  • Unified batch and streaming
  • Scalable metadata handling
WHY IT MATTERS
  • Eliminates data inconsistency
  • Concurrent reads and writes
  • Enforces data quality
  • Simplifies pipeline design
  • Reduces lake management complexity

C. How Delta Lake Works

Everything flows through the transaction log (_delta_log), an ordered record of every change ever made to the table.

Each INSERT, UPDATE, DELETE, or MERGE operation:

  • Computes a delta from the current version, adding or removing data files
  • Creates new Parquet data files if necessary
  • Commits a new version to the _delta_log, which becomes the current version

Each SELECT operation:

  • Gets the manifest of data files for the requested version from the _delta_log (latest by default)
  • Returns the data from the set of files in that version
▶ The transaction log in action
💡
Deletion vectors

On modern Databricks runtimes, UPDATE and DELETE do not always rewrite whole files. Deletion vectors mark individual rows as removed, making fine-grained DML much cheaper. OPTIMIZE later compacts the changes into clean files.

D. Delta Lake Operations

The transaction log enables operations a plain Parquet data lake cannot support:

Operation What it does
UPDATE, DELETE Fine-grained, condition-based row-level modifications
MERGE True upserts: update, insert, and delete in one atomic statement
Schema evolution Add or change columns, including CREATE OR REPLACE TABLE
Time travel Query previous versions with VERSION AS OF or TIMESTAMP AS OF
RESTORE Roll the table back to an earlier version

MERGE is the workhorse for incremental pipelines - change data capture feeds, slowly changing dimensions, and deduplication all reduce to a MERGE:

MERGE INTO target AS t
USING updates AS s
ON t.id = s.id
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

E. Reading and Writing with Spark

Delta Lake is the default table format on Databricks - no format() configuration is needed in either API:

Task Spark SQL DataFrame API
Read SELECT * FROM my_table spark.read.table("my_table")
Create CREATE TABLE ... AS SELECT df.write.saveAsTable("my_table")
Append INSERT INTO my_table df.write.mode("append").saveAsTable("my_table")
Overwrite INSERT OVERWRITE my_table df.write.mode("overwrite").saveAsTable("my_table")

Delta-specific SQL commands for inspection:

  • DESCRIBE HISTORY - the table's version history from the transaction log
  • DESCRIBE DETAIL - file count, size, location, and table properties

For more information see the Delta Lake statements reference.

F. Table Maintenance

Frequent small writes fragment a table into many small files, and metadata overhead slows every query that follows.

Command Purpose
OPTIMIZE my_table Compacts small files into fewer, larger ones
VACUUM my_table Permanently removes data files no longer referenced by the log
ℹ️
Use Predictive Optimization for Managed Tables

On Databricks much of this is automatic for managed tables with Predictive Optimization:

  • Optimized writes and auto compaction are enabled by default on new tables
  • Predictive optimization runs OPTIMIZE and VACUUM for Unity Catalog managed tables automatically, based on observed query patterns
⚠️
VACUUM breaks time travel

VACUUM deletes the files that old versions point to. After a VACUUM with the default 7-day retention, you can no longer time travel to versions older than the retention window. Always think before lowering the retention period.

G. Data Layout: From Partitioning to Liquid Clustering

How data files are organized determines how much a query can skip. The guidance here has changed significantly - older Spark material recommends techniques that are now legacy.

Strategy Status Notes
Hive-style partitioning (PARTITIONED BY) Legacy Rigid directory layout; prone to over-partitioning and small files
ZORDER BY (with OPTIMIZE) Legacy Multi-column clustering, but requires manual runs and full rewrites
Liquid clustering (CLUSTER BY) Recommended Incremental, flexible clustering; keys can change without rewriting the table
CLUSTER BY AUTO Recommended Databricks chooses and evolves clustering keys from your query patterns

Defining a liquid clustered table:

CREATE TABLE transactions (
  ...
)
CLUSTER BY (dateTime, franchiseID);
💡
Spark 4 era guidance

For new UC tables on Databricks, start with liquid clustering (or CLUSTER BY AUTO with predictive optimization) instead of Hive-style partitioning or ZORDER. Reserve physical partitioning for genuinely huge tables with a natural, low-cardinality boundary.

H. Apache Iceberg and UniForm

Apache Iceberg is the other major open table format, created at Netflix with goals similar to Delta Lake:

  • ACID transactions and schema evolution
  • Hidden partitioning and partition evolution
  • Branch and tag support

On Databricks the formats interoperate rather than compete:

  • Unity Catalog supports managed Iceberg tables, readable and writable from external Iceberg engines
  • UniForm lets a UC table expose Iceberg metadata, so Iceberg clients can read it in place
  • Spark 4 reads and writes Iceberg through the same DataFrame and SQL APIs used for Delta

Summary

  • Delta Lake brings ACID transactions to cloud storage through the _delta_log transaction log
  • Every write commits a new version; reads resolve a manifest of files from the log, enabling time travel and RESTORE
  • MERGE performs atomic upserts and powers incremental pipelines
  • OPTIMIZE compacts small files and VACUUM reclaims storage at the cost of old versions
  • Liquid clustering replaces Hive-style partitioning and ZORDER as the recommended layout strategy
  • Apache Iceberg is an alternative open table format; Unity Catalog and UniForm make the two interoperable
