3.1 Lecture - Optimizing Apache Spark

Knowing where and why your Spark applications spend their time

This lecture covers the optimization toolkit for Spark 4 on Databricks: partitioning and shuffles, Adaptive Query Execution, join strategies, caching, the Catalyst optimizer, and the monitoring tools that tell you which technique a workload actually needs.

By the end of this lecture, you will be able to:

  • Use the Spark UI and execution plans to monitor applications and identify bottlenecks

A. Understanding Spark Performance

Time in a Spark application goes to four places: compute, data movement, I/O, and coordination. Optimization starts with knowing which one dominates your workload.

Key factors affecting performance:

  • Resource utilization: CPU, memory, network, disk I/O
  • Data characteristics: size, format, distribution
  • Configuration settings and cluster setup

Common bottlenecks:

  • Data skew and uneven or inadequate partitioning
  • Excessive shuffling and data movement
  • Memory pressure and garbage collection

B. Spark Partitioning

Partitions are the unit of parallelism: every stage runs one task per partition. How data is partitioned determines memory use per executor, join and aggregation efficiency, and network traffic.

Where partition counts come from:

  • Initial partitions - set by the files or blocks read from a table or directory
  • Shuffle partitions - created by wide transformations (groupBy, join) or explicit repartition / coalesce
  • The default partitioner is the hash partitioner: hash(key) % numPartitions

What you can do:

Technique Effect
df.repartition(n) Full shuffle to exactly n evenly sized partitions
df.repartition(n, col) Shuffle, co-locating rows by a key column
df.coalesce(n) Reduce partition count without a full shuffle (accepts imbalance)

Sizing guidance:

  • Target roughly 100-200MB per shuffle partition
  • Keep the partition count at or above the number of cores, or cores sit idle
  • Watch task durations in the Spark UI: very short tasks (under ~50ms) suggest too many partitions
💡
AQE changed this game

On Spark 4 with Adaptive Query Execution enabled (the default), Spark coalesces shuffle partitions at runtime based on actual data sizes. Manual spark.sql.shuffle.partitions tuning is now mostly a legacy technique - reach for explicit repartition only when you have a specific layout requirement.

C. Shuffle Operations

The shuffle is Spark's most expensive operation: data is serialized, written to disk, sent across the network, and read back by the next stage.

  • Shuffles are triggered by wide transformations (groupBy, join, distinct, orderBy) and by repartition
  • Every shuffle is a stage boundary - the whole stage must finish before the next begins
  • Shuffle spill (memory to disk) is a key warning sign to monitor in the Spark UI

How to minimize shuffle impact:

  • Filter early, filter often - move less data through every downstream stage
  • Select only the columns you need before wide operations
  • Use broadcast joins for small tables so the large side never shuffles
  • Maintain consistent partitioning across operations where possible
What to Observe

In the Spark UI Stages tab, the Shuffle Read and Shuffle Write columns quantify data movement, and Spill (Memory) / Spill (Disk) reveal memory pressure. These four numbers diagnose most slow stages.

D. Adaptive Query Execution

Adaptive Query Execution (AQE) re-optimizes query plans at runtime using real statistics from completed shuffle stages. It is enabled by default in Spark 4.

AQE makes three major optimizations automatically:

Optimization What it fixes
Coalescing shuffle partitions Too many small post-shuffle partitions wasting task overhead
Skew join handling One giant partition stalling an entire stage
Dynamic join strategy switching A sort-merge join that should have been a broadcast join, once actual sizes are known
▶ How AQE re-optimizes at runtime
📝
What this means for you

Much of the manual tuning in older Spark material - fixing spark.sql.shuffle.partitions, hand-splitting skewed keys, forcing join order - is now handled by AQE. Your job is to verify it in the Spark UI (look for AQEShuffleRead in the plan) and step in only where AQE cannot help, such as the initial read layout and caching decisions.

E. Join Strategies

Joins are where shuffle costs concentrate. Spark chooses a strategy automatically, and the choice matters more than almost any other plan decision.

Strategy When Spark uses it Cost profile
Broadcast hash join One side fits under the broadcast threshold Small side copied to every executor; no shuffle of the large side
Sort-merge join Both sides large Both sides shuffled and sorted - the expensive default
Shuffle hash join One side moderately smaller Both sides shuffled, smaller side hashed

Influencing the choice:

from pyspark.sql.functions import broadcast
result_df = large_df.join(broadcast(small_df), "key")
  • The automatic broadcast threshold is controlled by spark.sql.autoBroadcastJoinThreshold
  • AQE can convert a planned sort-merge join to a broadcast join at runtime once it sees the true size
  • Project only needed columns before joining, and watch for join key skew in the Stages tab

F. DataFrame Caching

Caching persists a computed DataFrame in executor memory (and disk) so repeated use skips recomputation.

When to cache:

  • Multiple actions over the same transformed DataFrame
  • Expensive upstream transformations (joins, aggregations) feeding several outputs
  • Interactive analysis and iterative ML workloads

Cache management:

  • df.cache() marks the DataFrame; the first action actually populates the cache
  • Monitor the Storage tab in the Spark UI for size and memory fraction cached
  • Call df.unpersist() when finished - executor memory is a shared resource
⚠️
Caching is not free

Cached data competes with shuffle and execution memory. Caching a DataFrame used only once makes the workload slower, not faster. Cache deliberately, verify in the Storage tab, and unpersist when done.

G. Query Optimization with Catalyst

The Catalyst optimizer rewrites every query - SQL or DataFrame - into an optimized physical plan before execution.

What Catalyst does for you automatically:

  • Predicate pushdown - filters move down to the scan, so less data is read at the source
  • Column pruning - only the referenced columns are read from columnar formats
  • Filter combination - multiple filters collapse into one operation
  • Dynamic file pruning - join-driven file skipping on Delta tables at runtime

Inspect what it decided with explain():

df.explain()                   # physical plan
df.explain("formatted")        # readable plan with operator details
df.explain("extended")         # logical and physical plans
💡
Photon

On Photon-enabled runtimes, plan operators appear as PhotonScan, PhotonGroupingAgg, and so on - the vectorized native engine executing the same Catalyst plan faster. The optimization techniques in this lecture apply unchanged.

H. The Monitoring Toolkit

Every optimization claim should be verified with a measurement. Your toolkit on Databricks:

Tool What it tells you
Spark UI - Jobs / Stages Where time goes; shuffle read/write; spill; task skew
Spark UI - SQL / DataFrame Executed plans with per-operator rows and timing
Spark UI - Storage What is cached and how much memory it holds
Spark UI - Executors Resource usage, GC time, failed tasks per executor
explain() The plan before execution: join strategies, pushed filters
DESCRIBE DETAIL / DESCRIBE HISTORY Table file layout and operation metrics
Structured logging (Spark 4) JSON driver and executor logs, queryable with Spark itself
ℹ️
A monitoring workflow

Start at the SQL / DataFrame tab to find the slow query and the slow operator within it. Drill into the matching stage for shuffle and spill metrics. Only then change code or configuration - and re-measure after.

I. Best Practices

  • Use the Spark UI: track job progress, stage metrics, shuffle, storage, and executor detail
  • Filter early, filter often, and project only the columns you need
  • Prefer built-in functions; if custom logic is unavoidable, use pandas UDFs rather than row-by-row Python UDFs
  • Let AQE manage shuffle partition counts; reach for repartition only with a specific layout goal
  • Broadcast small join inputs and verify the strategy in the plan
  • Cache deliberately, verify in the Storage tab, and unpersist when done
  • Keep tables healthy with OPTIMIZE and liquid clustering - engine tuning cannot fix a fragmented table
