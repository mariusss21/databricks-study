    Recap 1 of 3 · ~4 min

    Unity Catalog decides where a file may land and who can read it

    Three-level names

    catalog.schema.object, where the object is a table, view, volume, function or model. Your Bronze table is e.g. prod.bronze.orders; your landing volume is prod.raw.landing, addressed as a path: /Volumes/prod/raw/landing/orders/.

    Volumes

    Governed storage for non-tabular files (landing drops, CSV/JSON, images, ML artifacts) in the same hierarchy as tables. Managed volume: UC owns the storage location. External volume: points at an existing cloud path inside an external location.

    Storage credential + external location

    A storage credential wraps a cloud identity (e.g. an IAM role or Azure managed identity). An external location = storage credential + cloud path (s3://…, abfss://…). Notebooks never embed long-lived keys, and mounts are not the pattern for new work.

    The grants that matter here

    READ VOLUME / WRITE VOLUME on volumes; READ FILES (and WRITE FILES) on external locations; plus USE CATALOG + USE SCHEMA on the parents. Can't list a path? Check grants first, Spark configs last.

    Managed vs external: what DROP does

    Managed table / volumeExternal table / volume
    Who owns the filesUnity Catalog (storage under the catalog/schema managed location)You (a path inside an external location)
    DROPMetadata gone; data files deleted after the recovery period (default 7 days; UNDROP TABLE works inside that window)Only the catalog entry goes; files stay in cloud storage
    Typical useDefault for Bronze/Silver/Gold tables (predictive optimization, simpler lifecycle)Data shared with outside tools or pre-existing paths
    SQL · what an admin sets up once (illustration)
    -- Storage credentials are usually created by an admin in Catalog Explorer or via the API/CLI.
CREATE EXTERNAL LOCATION IF NOT EXISTS partner_drop
  URL 's3://acme-landing/partner/'
  WITH (STORAGE CREDENTIAL acme_landing_cred)
  COMMENT 'Partner file drops';

CREATE EXTERNAL VOLUME IF NOT EXISTS prod.raw.partner
  LOCATION 's3://acme-landing/partner/';

CREATE VOLUME IF NOT EXISTS prod.raw.ops;   -- managed: checkpoints + schema locations

GRANT USE CATALOG ON CATALOG prod              TO `ingest-sp`;
GRANT USE SCHEMA  ON SCHEMA  prod.raw          TO `ingest-sp`;
GRANT READ VOLUME ON VOLUME  prod.raw.partner  TO `ingest-sp`;
GRANT READ VOLUME, WRITE VOLUME ON VOLUME prod.raw.ops TO `ingest-sp`;
GRANT USE SCHEMA, CREATE TABLE ON SCHEMA prod.bronze TO `ingest-sp`;

    Recap 2 of 3 · ~4 min

    Picking the loader, the discovery mode and the trigger

    COPY INTO (SQL)

    Loads files from a path into a Delta table. Retryable and idempotent: it records which files were loaded and skips them on re-run (unless COPY_OPTIONS ('force'='true')). Great for backfills, periodic drops, thousands of files, SQL-warehouse users.

    Auto Loader (cloudFiles)

    A Structured Streaming source that discovers new files incrementally and tracks them in the checkpoint (RocksDB) for exactly-once ingestion. Scales to millions of files, adds schema inference/evolution and rescued data.

    How Auto Loader finds files

    ModeHowCost profileWhen
    Directory listing defaultLists the input path every triggerGrows with the directory sizeSmall/medium dirs, quick start, labs, backfills
    File notification with file events recommendedConsumes cloud file events. With file events enabled on the external location, set cloudFiles.useManagedFileEvents = true (DBR 14.3 LTS+)Scales with new files, not total filesProduction, high-volume, long-lived paths (Databricks recommends it for most workloads)

    You can switch discovery modes across stream restarts and keep exactly-once guarantees, so migrating listing → file events doesn't need a full reload. For UC volumes, the docs list directory listing (DBR 13.3 LTS+) and file events (DBR 14.3 LTS+). Classic notifications without file events are not supported on volumes.

    Trigger: availableNow

    .trigger(availableNow=True) processes everything available when the query starts (possibly in several micro-batches), then stops. You get streaming semantics (checkpoint, exactly-once) with batch economics: schedule it as a job and pay only while it runs. On serverless compute it is the supported and recommended trigger; processingTime and continuous triggers raise an error there.

    Recap 3 of 3 · ~5 min

    Schema contracts on the way in

    Delta schema enforcement: a write whose columns don't match the table is rejected. Schema evolution is something you turn on on purpose (e.g. .option("mergeSchema","true") on the write, or an explicit ALTER TABLE … ADD COLUMNS). Auto Loader adds its own layer on the read side:

    • cloudFiles.schemaLocation: where the inferred schema and its history live. On first read, Auto Loader samples the first 50 GB or 1,000 files (whichever comes first) and writes the schema under _schemas in that directory. It can be the same directory as the checkpoint.
    • JSON/CSV/XML columns are inferred as strings by default. Set cloudFiles.inferColumnTypes = true for typed inference, or use cloudFiles.schemaHints for the columns you know.
    • When it infers, Auto Loader adds _rescued_data: a JSON blob of anything that didn't fit (missing column, type mismatch, case mismatch) plus the source file path.
    cloudFiles.schemaEvolutionModeOn a new column
    addNewColumns default without a schemaUpdates the schema in the schema location, then the stream fails once with UnknownFieldException. A restart resumes with the new column. Existing column types don't change. Run it as a Lakeflow Job with retries.
    rescueThe schema never evolves and the stream never fails on a schema change. New columns go into the rescued data column.
    failOnNewColumnsFails, and keeps failing until you update the provided schema or remove the offending file.
    none default with a provided schemaNo evolution. New columns are ignored, and nothing is rescued unless rescuedDataColumn is set. Doesn't fail.

    Also documented: addNewColumnsWithTypeWidening (Public Preview, DBR 16.4+) widens types such as int → long. You don't need it for the exam, but it's good to know it exists.

    The layer rule (Oct 12 pill)Bronze may evolve (keep everything, never lose a field). Silver is stricter (explicit schema, expectations, reviewed changes). Gold never widens silently: fail fast, review, then migrate with an explicit ALTER or pipeline change.

    End-to-end walkthrough · ~12 min

    A file lands, Bronze stays trustworthy, the shape changes

    Follow one orders feed through six steps. It's the same code you'll run in the lab (lab names: catalog workspace, schema dd_ingest).

    Step 1: Create the governed landing zone

    Two volumes: landing for the raw drops and ops for the checkpoint and schema location. Keeping ops state separate lets you grant a read-only group READ VOLUME on landing without giving it access to stream state.

    SQL
    CREATE SCHEMA IF NOT EXISTS workspace.dd_ingest;
CREATE VOLUME IF NOT EXISTS workspace.dd_ingest.landing COMMENT 'raw JSON drops';
CREATE VOLUME IF NOT EXISTS workspace.dd_ingest.ops     COMMENT 'checkpoints + schema locations';

    In production, the landing volume would usually be an external volume on the external location partners write to, while Bronze stays a managed table.

    Step 2: The first file lands

    JSON Lines (one object per line), dropped at /Volumes/workspace/dd_ingest/landing/orders/orders_001.json:

    Step 3: Auto Loader with schemaLocation + checkpoint under availableNow

    PySpark · notebook dd_bronze_orders
    from pyspark.sql import functions as F

CATALOG, SCHEMA = "workspace", "dd_ingest"
SOURCE      = f"/Volumes/{CATALOG}/{SCHEMA}/landing/orders/"
OPS         = f"/Volumes/{CATALOG}/{SCHEMA}/ops"
SCHEMA_LOC  = f"{OPS}/schemas/bronze_orders"       # inferred schema + history (_schemas)
CHECKPOINT  = f"{OPS}/checkpoints/bronze_orders"   # which files were ingested (exactly-once)
TARGET      = f"{CATALOG}.{SCHEMA}.bronze_orders"

raw = (spark.readStream.format("cloudFiles")
       .option("cloudFiles.format", "json")
       .option("cloudFiles.schemaLocation", SCHEMA_LOC)
       .option("cloudFiles.inferColumnTypes", "true")
       .option("cloudFiles.schemaEvolutionMode", "addNewColumns")   # the default, written out on purpose
       .load(SOURCE))

bronze = (raw
          .withColumn("_source_file", F.col("_metadata.file_path"))
          .withColumn("_ingested_at", F.current_timestamp()))

query = (bronze.writeStream
         .option("checkpointLocation", CHECKPOINT)
         .option("mergeSchema", "true")      # let Delta accept columns Auto Loader adds
         .trigger(availableNow=True)
         .toTable(TARGET))
query.awaitTermination()

    What exists after this run: _schemas/0 under the schema location (version 0 of the inferred schema, including _rescued_data), the file recorded in the checkpoint, and three rows in the Delta table, which now has its first commits in history.

    Step 4: Inspect Bronze: Delta gives you the audit trail

    SQL
    SELECT order_id, amount, status, _rescued_data, _source_file, _ingested_at
FROM workspace.dd_ingest.bronze_orders;

DESCRIBE HISTORY workspace.dd_ingest.bronze_orders;    -- one STREAMING UPDATE per micro-batch

    Re-run the notebook without new files and zero rows are added. That comes from the checkpoint. The table is UC-managed, so its lineage, owner, and grants live in the catalog, and time travel (VERSION AS OF) is your rollback.

    Step 5: A new field appears, handled by addNewColumns

    orders_002.json (new field: coupon_code)
    {"order_id": 1004, "customer_id": "C-099", "amount": 89.00, "currency": "BRL", "status": "PAID", "order_ts": "2026-10-19T09:12:00Z", "coupon_code": "SEMANA10"}
{"order_id": 1005, "customer_id": "C-042", "amount": 15.75, "currency": "BRL", "status": "PAID", "order_ts": "2026-10-19T09:15:30Z", "coupon_code": null}
    1. Run 1 after the drop: Auto Loader sees coupon_code and merges it into the schema (a new version under _schemas). Then the stream fails with UnknownFieldException. This is by design: it stops so the new schema takes effect on a clean restart.
    2. Run 2 (a manual rerun, or an automatic Lakeflow Job retry): the stream resumes with the new schema, mergeSchema lets Delta add coupon_code, and the old rows show NULL.
    Why the Job mattersIn a notebook you see the failure right away. In production nobody is watching at 3 a.m. Put the stream in a Lakeflow Job with retries so the one-time stop recovers on its own, which is exactly what the docs recommend. Serverless jobs also auto-optimize retries by default.

    Step 6: The same drift under rescue

    Change one line, and use a fresh schema location, checkpoint, and target (a new stream):

    PySpark (diff)

    Now the new field never fails the stream and never becomes a column. It lands in _rescued_data as JSON, together with the source file path:

       _rescued_data,

WHERE _rescued_data IS NOT NULL;

    Decision drill · ~8 min

    COPY INTO or Auto Loader?

    Exam framing (Oct 14 knowledge pill): ingestion choices are judged by volume, frequency, data type and Unity Catalog needs. Pick an answer for each card; the explanation shows either way. Score: 0 / 0

    Rule of thumb you can say out loudThousands of files, occasional or one-off loads, SQL-first team → COPY INTO. Millions of files, continuous or frequent arrival, schema drift, exactly-once across restarts → Auto Loader (with file events at high volume). SaaS apps or databases as the source → Lakeflow Connect (today's pill).

    Lab checklist

    Interview practice · ~8 min

    Senior-style questions

    Answer out loud first (about 2 minutes each), then reveal.

    1. Design file ingestion for a partner who drops ~50k JSON files a day into S3. It must be governed, re-runnable, and tolerant of schema drift.

    Governance: an admin creates a storage credential (IAM role) and an external location on the partner prefix, then an external volume over it. The ingestion service principal gets USE CATALOG/USE SCHEMA and READ VOLUME; nobody embeds keys or uses mounts. Checkpoints and schema state go in a separate ops volume where only the SP has WRITE VOLUME.

    Loader: Auto Loader. Arrival is continuous, the file count grows without bound, and the checkpoint gives exactly-once. At that volume I'd enable file events on the external location and use managed file events, so cost follows new files, not directory size.

    Schema: a schemaLocation, schema hints for the known keys, addNewColumns in Bronze, and _rescued_data kept for type mismatches. Silver reads Bronze with an explicit schema and expectations, and Gold changes go through review.

    Run + cost: availableNow in a Lakeflow Job on job or serverless compute, never on an all-purpose cluster. The job gets retries, so the one-time evolution stop heals itself, and a schedule or file-arrival trigger that matches the SLA. Delta history and time travel cover rollback, and _metadata.file_path plus an ingest timestamp trace each row back to its file.

    2. When would you still choose COPY INTO over Auto Loader?

    For bounded, batch-shaped loads: a one-off or periodic backfill, a few thousand files at a time, a SQL-first team on a SQL warehouse, or a quick idempotent load where streaming checkpoints would be overhead. COPY INTO is idempotent (already-loaded files are skipped unless you set force), supports mergeSchema, and is plain SQL. Its limit is scale. At millions of files, or with continuous arrival, Auto Loader wins with incremental discovery, schema evolution, and rescue. Databricks also generally points new incremental workloads to Auto Loader or declarative pipelines.

    3. Your Auto Loader stream failed overnight with UnknownFieldException. What happened, and what do you change?

    That's addNewColumns working as designed. A new field arrived, Auto Loader merged it into the schema in the schema location, and it stopped the stream so the next start uses the new schema. Nothing was lost, because the checkpoint knows where it stopped. The fix is operational, not code: run the stream as a Lakeflow Job with retries so the restart is automatic, and alert on schema changes so a person reviews the new field before Silver and Gold depend on it. If this table must not widen, use rescue (keep flowing, park the field) or failOnNewColumns (hard stop for a human). Also check that the write has mergeSchema, or the Delta sink will reject the wider DataFrame.

    4. A colleague dropped the Bronze table "to rebuild it" and the files are gone. Explain what happened and how you'd prevent it.

    It was a UC managed table, so DROP removed the metadata and Databricks deletes the data files after the recovery period (7 days by default). Inside that window, UNDROP TABLE can bring it back. An external table would have kept its files. To prevent it: least privilege (only the owner or a principal with MANAGE can drop), the job's service principal owns the tables, DDL goes through CI/CD rather than by hand, and the raw landing files are kept (an external volume with a retention policy) so Bronze can be rebuilt with a fresh checkpoint. Rebuilding is cheap when the raw layer is immutable and the ingestion can be replayed.

    Exam cheat sheet for this path

    • Three-level names. Volumes hold non-tabular files and are read by path: /Volumes/cat/sch/vol/….
    • READ/WRITE VOLUME on volumes, READ FILES on external locations, and always USE CATALOG + USE SCHEMA.
    • DROP a managed table → files deleted (after the recovery window). DROP an external table → files stay.
    • COPY INTO = idempotent, skips loaded files, thousands of files, batch. Auto Loader = incremental, checkpointed, millions of files.
    • Discovery modes: directory listing (the default; cost grows with the folder) vs file notification (file events; recommended at scale). You can switch modes across restarts.
    • AvailableNow = process what's there, then stop. It's the trigger to use on serverless.
    • Schema inference needs a schemaLocation. The default addNewColumns fails once, then a restart picks up the new schema. rescue → _rescued_data. With a provided schema, the default mode is none.
