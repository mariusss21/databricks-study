    Last week was three decisions, not three features

    Your Oct 19–25 pills (DB1–DB7) covered Lakeflow Connect, Auto Loader checkpoints and triggers, nested JSON, JDBC/REST jobs, tool choice and Bronze table design. The Oct 19 and Oct 23 deep dives already built Bronze end to end. Today is about the decisions: which tool, what makes a re-run safe, and what happens when the data's shape changes. Together they give you one pipeline you can re-run without worrying.

    Decision 1 · Tool

    Who owns the extract, and how does the source change?

    • Lakeflow Connect: Databricks-managed connectors for supported SaaS apps and databases (CDC). The platform runs the extraction and incremental state.
    • Auto Loader: files land in your storage or a UC volume, keep arriving, and may number in the millions.
    • COPY INTO: idempotent SQL batch loads of files, good for thousands of files or a one-off backfill.
    • JDBC/REST notebook as a Lakeflow Job: no managed connector exists, so you own the extract code, the watermark and the retries.
    Decision 2 · Re-run safety

    What stops a re-run from loading the same data twice?

    • The Auto Loader checkpoint records which files were discovered and committed. A restart continues from it, and files already processed are skipped.
    • availableNow processes the backlog and then stops, so a scheduled Job is a cheap incremental batch. A continuously running stream keeps compute up for low latency.
    • COPY INTO keeps its own record of loaded files. Connect keeps its own cursor. With JDBC/REST, you build idempotency yourself.
    Decision 3 · Shape & drift

    What happens when the payload changes, and can every row be traced?

    • Land nested data as STRUCT (inferred), as STRING (raw), or as VARIANT (flexible, queryable).
    • cloudFiles.schemaEvolutionMode controls what happens to new fields: add them, rescue them, fail, or ignore them.
    • Append-only Bronze with _metadata file columns and an ingest timestamp lets you trace any later Silver row back to its source file.
    Rule of thumb from DB5: choose the tool by who owns the extract and how often the schema changes, not by which Spark read API you already know.

    5 · Hands-on · ~20 min · Free Edition (serverless)

    Build it, re-run it, drift it

    This is a short version of the Oct 19 build. The goal is not "Auto Loader works". The goal is to prove the three decisions: the second run adds nothing (decision 2), and an unexpected field is caught without failing the load (decision 3). Create a new notebook on serverless compute and paste the cells in order.

    Free Edition is serverless-only. On serverless compute, Auto Loader streams use .trigger(availableNow=True); time-interval triggers aren't supported there. Databricks' serverless limitations page points continuous workloads to a continuous-mode pipeline, or to Trigger.AvailableNow() in a continuous job. That is exactly the "incremental batch" pattern we want here.

    Cell 1 · Paths and names (UC volume, separate state folders)

    CATALOG = "workspace"   # Free Edition's default catalog; change if yours differs
SCHEMA  = "ingest_lab"
spark.sql(f"CREATE SCHEMA IF NOT EXISTS {CATALOG}.{SCHEMA}")
spark.sql(f"CREATE VOLUME IF NOT EXISTS {CATALOG}.{SCHEMA}.landing")

BASE       = f"/Volumes/{CATALOG}/{SCHEMA}/landing"
SOURCE     = f"{BASE}/raw/orders"                      # where files land
SCHEMA_LOC = f"{BASE}/_state/orders_bronze/schema"     # Auto Loader schema versions
CHECKPOINT = f"{BASE}/_state/orders_bronze/checkpoint" # files seen + commits
TARGET     = f"{CATALOG}.{SCHEMA}.orders_bronze"

    The state folders sit outside SOURCE, so Auto Loader never mistakes its own state files for input. One checkpoint belongs to one stream and one target. Never share it.

    Cell 2 · Land two nested JSON files

    import json

def land(name, records):
    # JSON Lines: one object per line (Auto Loader's default for JSON)
    dbutils.fs.put(f"{SOURCE}/{name}", "\n".join(json.dumps(r) for r in records), overwrite=True)

land("orders_001.json", [
    {"order_id": 1001, "order_ts": "2026-10-26T08:01:00Z", "amount": 59.9,
     "customer": {"id": "C-1", "country": "BR"}, "items": [{"sku": "A1", "qty": 2}]},
    {"order_id": 1002, "order_ts": "2026-10-26T08:05:00Z", "amount": 12.0,
     "customer": {"id": "C-2", "country": None}, "items": [{"sku": "B7", "qty": 1}]},
])
land("orders_002.json", [
    {"order_id": 1003, "order_ts": "2026-10-26T08:20:00Z", "amount": 230.0,
     "customer": {"id": "C-3", "country": "US"}, "items": [{"sku": "A1", "qty": 1}, {"sku": "C3", "qty": 4}]},
    {"order_id": 1004, "order_ts": None, "amount": None,
     "customer": {"id": "C-4", "country": "PT"}, "items": []},
])
display(dbutils.fs.ls(SOURCE))

    Cell 3 · The pipeline: all three decisions in about 20 lines

    from pyspark.sql import functions as F

def run_bronze():
    raw = (spark.readStream
        .format("cloudFiles")                                  # decision 1: files in a volume → Auto Loader
        .option("cloudFiles.format", "json")
        .option("cloudFiles.schemaLocation", SCHEMA_LOC)       # decision 3: schema is inferred once, versioned here
        .option("cloudFiles.schemaEvolutionMode", "rescue")    # decision 3: never fail, never evolve, rescue instead
        .option("rescuedDataColumn", "_rescued_data")
        .load(SOURCE))

    bronze = raw.select(
        "*",                                                   # payload as landed (JSON → strings, nested → struct)
        F.col("_metadata.file_path").alias("source_file"),     # lineage: which file
        F.col("_metadata.file_modification_time").alias("source_file_mtime"),
        F.current_timestamp().alias("ingested_at"))            # lineage: which run

    q = (bronze.writeStream
        .option("checkpointLocation", CHECKPOINT)              # decision 2: files already committed are skipped
        .trigger(availableNow=True)                            # decision 2: drain the backlog, then stop
        .toTable(TARGET))                                      # append-only UC Delta table
    q.awaitTermination()

run_bronze()
display(spark.sql(f"SELECT source_file, count(*) AS row_count FROM {TARGET} GROUP BY source_file ORDER BY source_file"))
display(spark.table(TARGET))

    Expected: 4 rows from 2 files. Look at the column types. Because JSON carries no types, Auto Loader infers every column as a string, including nested fields, unless you set cloudFiles.inferColumnTypes or schema hints. So customer is a STRUCT of strings and amount is a STRING. That's fine for Bronze, and casting is Silver's job (see section 8).

    Cell 4 · Re-run: prove "no duplicates"

    run_bronze()   # same code, same checkpoint, no new files

display(spark.sql(f"""
  SELECT count(*) AS row_count, count(DISTINCT order_id) AS distinct_orders,
         count(DISTINCT ingested_at) AS runs_that_wrote_rows
  FROM {TARGET}"""))
display(spark.sql(f"DESCRIBE HISTORY {TARGET}").select("version", "timestamp", "operation", "operationMetrics"))

    Expected: still 4 / 4 / 1. The checkpoint already lists both files, so the second availableNow run finds nothing new and stops. In the history, only one version wrote rows. This is what "safe to re-run" means in practice: a Job retry, a manual re-run, or a double-click on "Run now" all end up in the same state.

    What would break it? (a) Deleting or changing CHECKPOINT while keeping the table: every file is new again, so you get duplicates. (b) Overwriting a file under the same name: by default Auto Loader doesn't pick up the new version, because cloudFiles.allowOverwrites is false. Producers should write new file names. (c) Two jobs writing with the same checkpoint at the same time. In the Job, use max_concurrent_runs = 1.

    Cell 5 · Drift: a file with a field nobody announced

    land("orders_003.json", [
    {"order_id": 1005, "order_ts": "2026-10-26T09:10:00Z", "amount": 99.0,
     "customer": {"id": "C-5", "country": "US"}, "items": [{"sku": "C3", "qty": 1}],
     "coupon_code": "BLACKFRIDAY"},                      # ← not in the inferred schema
])
run_bronze()

display(spark.sql(f"""
  SELECT order_id, _rescued_data, source_file, ingested_at
  FROM {TARGET} WHERE _rescued_data IS NOT NULL"""))
display(spark.sql(f"SELECT count(*) AS row_count FROM {TARGET}"))   # 5: only the new file was read

    Expected: the run succeeds, the table now has 5 rows, and order 1005 has _rescued_data containing coupon_code as a JSON string. Nothing was lost and nothing failed. The table schema did not change. That is the rescue contract.

    Same drift, other modes (from the Auto Loader schema docs):
    • addNewColumns (the default when you don't provide a schema): the stream fails with UnknownFieldException after it adds coupon_code to the schema. The restart then continues with the new column. That's why Databricks recommends running Auto Loader in Lakeflow Jobs with retries.
    • addNewColumnsWithTypeWidening: like addNewColumns, but it also widens supported types (for example int → long). Unsupported type changes go to the rescued column.
    • failOnNewColumns: the stream fails and stays failed until you update the schema or remove the file. This is a strict contract.
    • none: new columns are ignored and nothing is rescued unless rescuedDataColumn is set.
    Want flexibility instead of inferred columns? Land the whole record as VARIANT with .option("singleVariantColumn", "payload"). Drift then lives inside one column, and you decide on structure in Silver.

    job.json. There is no cluster spec, so on Free Edition the task runs on serverless:

    {
  "name": "ingest_lab_orders_bronze",
  "max_concurrent_runs": 1,
  "tasks": [
    {
      "task_key": "orders_bronze",
      "notebook_task": {
        "notebook_path": "/Users/<you>/ingest_lab/bronze_orders",
        "source": "WORKSPACE"
      },
      "max_retries": 2,
      "min_retry_interval_millis": 10000
    }
  ]
}
    databricks jobs create --json @job.json     # → {"job_id": 123...}
databricks jobs run-now <job_id>            # waits for the run; Bronze unchanged if no new files
databricks jobs run-now <job_id>            # again: still no duplicates (checkpoint)

    Why these settings connect: max_retries is what makes addNewColumns self-healing (fail → retry → new schema). max_concurrent_runs: 1 protects the checkpoint. A schedule plus availableNow gives you incremental batch without an always-on cluster.

    6 · Interview questions · ~6 min

    Answer out loud first, then reveal

    These are senior-DE system-design questions. They cover the same ground as the Associate exam scenarios, but they ask you to justify your choices.

    Q1. "Your Bronze ingestion job failed halfway and someone re-ran it. How do you know you don't have duplicates?"

    Strong answer: Re-run safety comes from the state the ingestion tool keeps, not from hoping nobody re-runs the job. With Auto Loader, the checkpoint records which files were discovered and committed, and the Delta sink commits through the checkpoint. A restart continues from the last committed point, and files already ingested are skipped. I'd prove it with lineage columns: count rows per source_file and per ingested_at. A file should appear in only one ingest batch. On the job side I set max_concurrent_runs = 1 so two runs never share a checkpoint. I treat the checkpoint as part of the table. If I delete one, I replay the other too. With a JDBC/REST notebook there's no checkpoint, so I'd use a watermark table and an idempotent write (MERGE on the key, or replaceWhere on the extract window).

    Q2. "addNewColumns or rescue for a Bronze table fed by a partner's JSON?"

    Strong answer: It depends on who consumes the drift. addNewColumns keeps Bronze as close to the source as possible. New fields become columns, but the stream stops once on each change and relies on a Job retry to continue, and the schema grows without review. rescue never fails and never changes the schema. Unknown fields go into _rescued_data, where I can alert on _rescued_data IS NOT NULL and decide to promote a field on purpose. For a partner feed I don't control, I'd pick rescue or land it as VARIANT. For an internal producer with a data contract, failOnNewColumns can be the right choice, because there a breaking change should stop the line. In every case, nothing is silently dropped. That's the only option I'd rule out (none without a rescued column).

    Q3. "availableNow or a continuously running stream?"

    Strong answer: It's a choice between latency and cost, and the code is the same. availableNow processes everything that's available (in multiple batches if needed) and then stops. On a schedule, that gives incremental batch with exactly-once file handling and no idle compute. A continuously running stream keeps compute up to get low latency. On serverless jobs, time-interval triggers aren't supported. For continuous needs Databricks points you to a continuous-mode pipeline, or to availableNow in a continuous job. Because the checkpoint is the same, I can move from scheduled to continuous later without changing the Bronze table or re-ingesting anything.

    Q4. "Why not MERGE into Bronze to dedupe on ingest?"

    Strong answer: Bronze's job is to keep a faithful, replayable record of what arrived, with _metadata file columns and an ingest timestamp so every Silver row can be traced back to its source file and batch. Append-only writes are cheap, they work naturally with streaming, and they never destroy evidence. If the producer sends a duplicate, I want to see it in Bronze. Dedup by business key ("latest record wins") belongs in Silver, where the rules are explicit and testable. File-level exactly-once is the tool's job (checkpoint). Record-level dedup is a modeling decision. Mixing the two in Bronze makes both harder to reason about.

    Q5. "When would you choose COPY INTO or Lakeflow Connect over Auto Loader?"

    Strong answer: COPY INTO is a good fit when a SQL user needs an idempotent, re-runnable batch load of a manageable number of files, such as a one-off backfill or a small periodic drop. It skips files it has already loaded, so re-running is harmless. Auto Loader is the better fit for continuous arrival and very large file counts, and it adds schema inference/evolution and the rescued data column. Lakeflow Connect sits on a different axis: the source isn't files at all, it's a supported SaaS app or database. The managed connector owns extraction, incremental state and CDC, so I don't write or operate any of that. If no managed connector exists, I write a JDBC/REST notebook and run it as a Lakeflow Job, and I own the watermark.

    Teaser: Bronze → Silver starts with a name, a cast and a null rule

    This week's theme is Bronze-to-Silver transforms. Today's pill covers cleaning. Here's the first step, run against the table you just built. Joins, explode, dedup and tuning come later in the week.

    from pyspark.sql import functions as F

bronze = spark.table("workspace.ingest_lab.orders_bronze")   # by UC name, never by path

silver_preview = (bronze
    .select(
        F.col("order_id").cast("bigint").alias("order_id"),
        F.to_timestamp("order_ts").alias("order_ts"),
        F.col("amount").cast("decimal(10,2)").alias("amount"),
        F.coalesce(F.col("customer.country"), F.lit("UNKNOWN")).alias("country"),
        "source_file", "ingested_at")                       # lineage travels with the row
    .where(F.col("order_id").isNotNull()))

display(silver_preview)
