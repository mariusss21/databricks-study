    1 · Recap · ~8 min

    Welcome back: W44 in five rules

    You've had a week off, so this is a re-entry review rather than new material. Your W44 pills (DB1–DB5, Oct 26–30) covered the code that turns Bronze into Silver and Gold. Each card below is one pill reduced to the single rule worth remembering. After that, the rest of the lesson runs all five on one small dataset, so you can see how they fit together.

    DB1 · Bronze → Silver cleaning

    Bad values become NULLs you can count, not failed jobs.

    • CAST fails the query on bad input when ANSI mode is on (the Databricks SQL default). try_cast / try_to_timestamp return NULL instead.
    • coalesce(a, b) is the first non-null value. Use it only when the fallback means something.
    • na.drop(subset=[key]) (or WHERE key IS NOT NULL) for rows you can't use. na.fill only fills columns whose type matches the fill value.
    • Always count the NULLs that try_* produced.
    DB2 · Joins & unions

    Know what a join will do to the row count before you run it. Union by name, not by position.

    • inner drops unmatched rows. left keeps all left rows. semi = "has a match" (left columns only, never duplicates). anti = "has no match" (orphan check).
    • Duplicate keys on the dimension side fan out the fact rows.
    • BROADCAST a small dimension to skip the shuffle on the big side.
    • union matches by position (like UNION ALL). unionByName matches by name.
    DB3 · Column & row surgery

    Column operations never change the row count. Generators do. Ask "one row per what?" after every explode.

    • select / withColumn / alias / split leave the number of rows alone.
    • explode: one row per element, and parents with a NULL or empty array disappear.
    • explode_outer: those parents stay, as one row with a NULL element.
    • Order-level measures (the total) don't belong on line-level rows.
    DB4 · Dedup & upsert

    Get one row per key with a survivor rule you chose, then use a guarded MERGE so re-runs do nothing.

    • row_number() OVER (PARTITION BY key ORDER BY ts DESC, tiebreak DESC) = 1, written with QUALIFY in Databricks SQL.
    • dropDuplicates([key]) doesn't let you pick the survivor. rank ties can keep two rows.
    • MERGE INTO is one atomic Delta commit. It fails if several source rows try to update the same target row.
    • WHEN MATCHED AND s.ts > t.ts makes the second run a no-op and blocks late, stale records.
    DB5 · Aggregations & profiling → Gold

    Declare Gold's grain before you aggregate, and know what each count leaves out.

    • count(*) counts rows. count(col) skips NULLs. count(DISTINCT col) is exact and skips NULLs.
    • approx_count_distinct (HyperLogLog++) is cheaper for huge, high-cardinality columns.
    • describe() gives count/mean/stddev/min/max. summary() adds the 25/50/75% percentiles.
    • Reconcile Gold totals against Silver. Distinct counts don't add up across groups.
    The thread · Grain

    Every step either keeps the grain, changes it on purpose, or breaks it by accident.

    • explode multiplies rows (new grain: lines).
    • joins can fan rows out (broken grain).
    • dedup restores one row per key.
    • Gold picks a new, coarser grain on purpose.
    • Profiling counts are how you prove which one happened.
    Quick self-check before moving on: without scrolling up, can you say what count(amount) does with a NULL amount, and what explode does with an empty array? If either took more than two seconds, re-read that card.

    DB1 · Clean

    Type it, null the garbage, drop what has no key

    -- Cell 2 (SQL): DB1 cleaning as a view (re-evaluated every time Bronze grows)
CREATE OR REPLACE TEMP VIEW orders_clean AS
SELECT
  order_id,
  customer_id,
  try_to_timestamp(order_ts, 'yyyy-MM-dd HH:mm:ss')                 AS order_ts,
  coalesce(try_to_timestamp(updated_at, 'yyyy-MM-dd HH:mm:ss'),
           try_to_timestamp(order_ts,   'yyyy-MM-dd HH:mm:ss'))     AS change_ts,
  try_cast(amount AS DECIMAL(10,2))                                  AS amount,  -- 'abc' -> NULL
  items,
  _ingested_at
FROM bronze_orders
WHERE order_id IS NOT NULL;                                          -- = na.drop(subset=["order_id"])

SELECT count(*) AS clean_rows, count(amount) AS rows_with_amount FROM orders_clean;  -- 7, 6
    • Row 5 has no order_id, so WHERE order_id IS NOT NULL (= na.drop(subset=["order_id"])) removes it. 8 → 7
    • Row 3's 'abc' becomes NULL through try_cast. A plain CAST with ANSI on would have failed the whole job over one value. count(*) = 7 but count(amount) = 6. That gap of 1 is your data-quality metric.
    • change_ts = coalesce(updated_at, order_ts) gives every row a "version time". This is a meaningful fallback (no update means the creation time is the version), not a sentinel.

    grain: still one row per arrival. Cleaning changes values, not the meaning of a row.

    DB4 · Upsert

    MERGE INTO silver_orders, then run it again

    MERGE INTO silver_orders AS t
USING (
  SELECT * FROM orders_clean
  QUALIFY row_number() OVER (PARTITION BY order_id
                             ORDER BY change_ts DESC, _ingested_at DESC) = 1
) AS s
ON t.order_id = s.order_id
WHEN MATCHED AND s.change_ts > t.change_ts THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

    1 (empty target)5055Nothing matches, so every source row goes through WHEN NOT MATCHED
    2 (same input)0005All 5 match, but none has s.change_ts > t.change_ts, so the run is a no-op

    Two things make this idempotent. Dedup guarantees at most one source row per key, and without it MERGE raises an error when several source rows try to update the same target row. The guard on the matched clause turns "same data again" into zero changes and stops late, older records from overwriting newer ones. The steps below use the state after run 2.

    6 · Exam-style & interview questions · ~7 min

    SQL first, like the exam. Answer out loud, then reveal.

    Q1. SELECT id, name FROM a UNION SELECT name, id FROM b. What goes wrong, and how do you fix it in SQL and in PySpark?

    Strong answer: SQL set operators (UNION, UNION ALL, INTERSECT, EXCEPT) match columns by position, so b.name lands in id. If the types are compatible it won't even error, so the data is just wrong. Fix it in SQL by listing the columns in the same order on both sides. In PySpark, df.union(other) is also positional, while df.unionByName(other) matches by name, and allowMissingColumns=True fills columns missing on one side with NULL (useful for drifting Bronze batches). Second trap: SQL UNION removes duplicate rows and UNION ALL keeps them. The DataFrame union/unionByName methods behave like UNION ALL. Add .distinct() if you really want set semantics.

    Q2. Orders has an items array. Some orders have items = [] or NULL. Analysts complain those orders are missing from the flattened table. What happened?

    Strong answer: The flattening used explode(items), which emits one row per element and zero rows for an empty or NULL array, so those parents disappear. explode_outer(items) (SQL: SELECT order_id, explode_outer(items) AS item FROM orders, or LATERAL VIEW OUTER explode(items) t AS item) keeps each such parent as one row with a NULL item. In our sample that's 9 rows vs 11. Then I'd ask the grain question. If the table is "one row per order line", explode is right, and orders without lines belong in the orders table. If every order must appear in this table, use explode_outer. Either way, never put order-level totals on the exploded rows, or sum fans out (280.50 became 761.50 in our data).

    Q3. Why use ROW_NUMBER() … QUALIFY instead of dropDuplicates(["order_id"]) for "latest record wins"? Why not RANK()?

    Strong answer: QUALIFY row_number() OVER (PARTITION BY order_id ORDER BY change_ts DESC, _ingested_at DESC) = 1 keeps exactly one row per key, and I choose which one through the ORDER BY. The deterministic tiebreaker means re-runs pick the same survivor. QUALIFY filters on a window result without a wrapping subquery, the way HAVING filters on aggregates. dropDuplicates(["order_id"]) also returns one row per key, but which row survives isn't specified, so it might keep the stale 80.00 version of o1002. dropDuplicates() with no columns (or DISTINCT *) only removes rows that are identical in every column, so a resend with a different _ingested_at survives (7 rows, not 5). RANK()/DENSE_RANK() give ties the same number, so = 1 can return two rows per key and the MERGE then fails. For streams, dropDuplicatesWithinWatermark bounds the state.

    Q4. Walk through what this MERGE does on the first and second run, and what happens if the source has two rows for the same order_id. 
    MERGE INTO silver_orders t USING updates s ON t.order_id = s.order_id
WHEN MATCHED AND s.change_ts > t.change_ts THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

    Strong answer: MERGE joins the source to the target on the ON condition and applies the clauses in a single atomic Delta commit. Readers see all of it or none of it. For each source row: if it matches a target row, the first WHEN MATCHED clause whose condition is true runs. Here that's an update only when the source is newer, and otherwise nothing happens. If it doesn't match, WHEN NOT MATCHED inserts it. Run 1 on an empty target inserts 5. Run 2 with the same source matches all 5, but the guard is false, so 0 rows are affected. The table's content is the same after any number of runs, which is what idempotent means. Without the guard, run 2 would rewrite 5 rows with identical values: the content is still correct, but it's wasted work, and a late, older record could overwrite a newer one. If two source rows match the same target row and both try to update or delete it, Delta raises an error (multiple source rows matched). That's why you dedup the source first. Watch out: an insert-only MERGE with duplicate source keys and no existing match would insert both. UPDATE SET */INSERT * need matching column names, and WHEN NOT MATCHED BY SOURCE (delete or flag target rows missing from the source) is only safe when the source is a full snapshot.

    Q5. silver_orders has 5 rows and one NULL amount. What do count(*), count(amount), count(DISTINCT customer_id), avg(amount) return?

    Strong answer: count(*) = 5, because it counts rows, NULLs included. count(amount) = 4, because count(col) skips NULLs. count(DISTINCT customer_id) = 4 (c1, c2, c3, c9). It's exact and also ignores NULLs. avg(amount) = 280.50 / 4 = 70.125, not 280.50 / 5, because avg, sum, min and max all ignore NULLs. On a billion-row, high-cardinality column I'd use approx_count_distinct(customer_id) (HyperLogLog++, default relative standard deviation 5%). It's much cheaper than an exact distinct, which has to move the distinct values through the shuffle. For finance or reconciliation I'd keep it exact. And the gap between count(*) and count(amount) is how I'd measure how many bad amounts try_cast turned into NULLs.

    Q6. SELECT CAST('abc' AS DECIMAL(10,2)) fails your Silver job. Is try_cast the fix?

    Strong answer: With ANSI mode on (spark.sql.ansi.enabled, the default in Databricks SQL), an invalid CAST raises an error, so one bad value fails the whole job. try_cast('abc' AS DECIMAL(10,2)) returns NULL, and try_to_timestamp does the same for timestamp strings that don't parse. So yes, it keeps the pipeline running, but only half the fix. try_cast hides bad data, so I'd also measure it (count(*) - count(amount), or amount_raw IS NOT NULL AND amount IS NULL) and route those rows to a quarantine table or an expectation, so they're tracked rather than silently turned into NULLs. Keep plain CAST for columns where a bad value should stop the line, like the primary key.
