    Four pills, one design decision

    Last Friday ended with an append-only, re-runnable Bronze: Auto Loader checkpoints, CDC landed as raw change rows, and dedup/replay handled at Silver. This week's DE pills (DE1–DE4) cover what happens next. Today's claim is simple: you can't build trustworthy history (SCD2) or correct facts unless every row passed a quality gate first and every table has a declared, tested grain. A senior engineer designs these four together.

    DE1 · Quality & conformance
    • Validate (is the row usable?) vs conform (cast, rename, standardize codes and time zones).
    • Every rule gets an explicit action: warn, drop, fail, or quarantine.
    • LDP expectations: EXPECT, ON VIOLATION DROP ROW, ON VIOLATION FAIL UPDATE (Python: expect, expect_or_drop, expect_or_fail, expect_all*).
    • Quarantine = the inverted rule writes bad rows with a reason to their own table. Delta NOT NULL/CHECK constraints are the last line of defense on the table itself.
    DE2 · Dimensional basics
    • Grain first: "one row per ___" before any column list.
    • Facts = events/measures at a grain. Dims = descriptive context.
    • Surrogate keys decouple the warehouse from source IDs and let one customer have many versions.
    • Unknown member (-1): a fact row never disappears because its dimension row is missing or late.
    DE3 · Grain control
    • Nested arrays become child tables, one per grain (posexplode_outer keeps a position and keeps parents with empty arrays).
    • Fan-out: join two "many" sides to the same parent and every measure multiplies.
    • Fix: aggregate the many side to the parent grain first, then join.
    • Prove it: uniqueness on the declared key, row-count reconciliation.
    DE4 · SCD1 vs SCD2
    • Type 1 overwrites (no history). Type 2 closes the old row and opens a new version (__START_AT/__END_AT or valid_from/valid_to).
    • Pick Type 2 per attribute: only what the business reports history on.
    • Facts join on the surrogate key as of event time.
    • Build with MERGE INTO by hand or AUTO CDC ... STORED AS SCD TYPE 2.
    Tie-back to Gerald's track this week: DB1 cleaning (casts, null rules) is the conform half of DE1. DB2 joins are where fan-out happens. DB3 explode is how you change grain. DB4 dedup and MERGE INTO is the engine under SCD2.

    The one-sentence version

    Gate → grain → history → fact → test. Each step depends on the one before it. A bad row that passes the gate becomes a bad version in the dimension. An undeclared grain becomes a doubled revenue number. A fact joined on the business key instead of the versioned surrogate key becomes a fan-out.

    The gate: an explicit action for every rule

    The scenario: an e-commerce company lands bronze.orders_raw (JSON orders with nested items and payments arrays) and bronze.customers_cdc (change rows from the customer DB). Before anything is reshaped, every row goes through a gate.

    The four actions and when each one fits

    ActionLDP SQLUse whenCost of choosing wrong
    Warn (keep, count)CONSTRAINT c EXPECT (cond)The row is still usable and the issue is cosmetic or fixable downstreamBad values flow into reports, but the metrics show it
    Drop... ON VIOLATION DROP ROWKnown noise that nobody will ever fix (test records, heartbeats)You lose evidence. Only the count in the event log remains
    Fail... ON VIOLATION FAIL UPDATEA systemic break where continuing would corrupt targets (for example the sequencing column is missing)The pipeline stops. Fine for contract breaks, too much for one bad row
    Quarantineinverted rule → separate table, or a flag columnThe row matters to the business and someone must fix or replay itNeeds an owner and a replay path, or it becomes a graveyard
    -- Lakeflow Declarative Pipeline (SQL). Gate on the orders feed.
CREATE OR REFRESH STREAMING TABLE orders_gated (
  CONSTRAINT has_order_id   EXPECT (order_id IS NOT NULL),
  CONSTRAINT positive_lines EXPECT (NOT exists(items, i -> i.price <= 0 OR i.qty <= 0))
) AS
SELECT *,
  CASE WHEN order_id IS NULL                                THEN 'null_order_id'
       WHEN items IS NULL OR size(items) = 0                THEN 'no_items'
       WHEN exists(items, i -> i.price <= 0 OR i.qty <= 0)  THEN 'non_positive_amount'
  END AS dq_reason                       -- NULL means the row passed
FROM STREAM(bronze.orders_raw);

-- Downstream: good rows feed Silver, flagged rows feed quarantine (with the reason).
CREATE OR REFRESH MATERIALIZED VIEW orders_quarantine AS
SELECT * FROM orders_gated WHERE dq_reason IS NOT NULL;

    This is the quarantine-flag pattern: the expectations are warn-only, so their pass/fail counts land in the pipeline event log, and the dq_reason column decides routing. Nothing disappears silently, and bronze rows = silver rows + quarantine rows becomes a test you can run.

    Accuracy note: DROP ROW keeps only the count of dropped rows in the event log, not the rows themselves. If anyone might ask "which orders were dropped and why?", you want quarantine, not drop.

    Exercise: pick the action for each rule

    Decide first, then click. The explanation tells you what a senior reviewer would expect.

    Table-level backstop: after the gate, a Delta constraint like ALTER TABLE silver.order_items ADD CONSTRAINT positive_price CHECK (price > 0) makes any later writer that skips the gate fail. Expectations decide what to do with rows. Constraints protect the table no matter who writes to it.

    Grain: one table per "one row per ___"

    An order has two independent arrays. If you keep them in one table you have no clear grain. Split them:

    TableGrain (one row per…)KeyHow
    silver.ordersorderorder_idselect the scalar columns
    silver.order_itemsorder line(order_id, line_no)posexplode_outer(items), line_no = pos + 1
    silver.order_paymentspayment(order_id, payment_no)posexplode_outer(payments)
    from pyspark.sql import functions as F

items = (spark.table("orders_gated").where("dq_reason IS NULL")
  .select("order_id", "customer_id", "order_ts",
          F.posexplode_outer("items").alias("pos", "item"))
  .select("order_id", (F.col("pos") + 1).alias("line_no"), "customer_id", "order_ts",
          F.col("item.sku").alias("sku"), F.col("item.qty").alias("qty"),
          F.col("item.price").alias("price"))
  .withColumn("line_amount", F.col("qty") * F.col("price")))

    Why posexplode_outer? pos gives a deterministic line number, so (order_id, line_no) is the same key on every re-run, as long as the source keeps array order stable (if it doesn't, use a source line ID). _outer keeps an order whose array is empty or null, with a null position, instead of silently removing the parent. In our pipeline the gate already quarantined orders with no items, so _outer is defense in depth.

    History: dim_customer as SCD2, declared then hand-built

    The business reports revenue by segment and country "as it was at order time", so those two attributes get Type 2. Email is contact data: nobody reports on last month's email, so it's Type 1 (overwrite in place).

    A. Declared: AUTO CDC in a Lakeflow pipeline

    -- 1) Gate the CDC feed (per-rule actions from the exercise)
CREATE OR REFRESH STREAMING TABLE customers_cdc_clean (
  CONSTRAINT has_lsn  EXPECT (lsn IS NOT NULL)         ON VIOLATION FAIL UPDATE,
  CONSTRAINT not_test EXPECT (customer_id NOT LIKE 'TEST-%') ON VIOLATION DROP ROW,
  CONSTRAINT valid_op EXPECT (op IN ('I', 'U', 'D'))   -- warn here; inverted rule feeds a quarantine table
) AS SELECT * FROM STREAM(bronze.customers_cdc);

-- 2) Declare the target, then the flow
CREATE OR REFRESH STREAMING TABLE dim_customer;

CREATE FLOW dim_customer_scd2 AS AUTO CDC INTO dim_customer
FROM stream(customers_cdc_clean)
KEYS (customer_id)
APPLY AS DELETE WHEN op = 'D'
SEQUENCE BY lsn
COLUMNS * EXCEPT (op, lsn, ingested_at)
STORED AS SCD TYPE 2
TRACK HISTORY ON segment, country;

    In practice the flow reads only the rows that passed valid_op (add WHERE op IN ('I','U','D') in a view between them). What each clause buys you:

    • KEYS (customer_id): the business key. Each key's versions are tracked independently.
    • SEQUENCE BY lsn: the source order, not arrival order. Late events are put in their correct place in history. NULL sequencing values aren't supported, which is why has_lsn fails the update.
    • STORED AS SCD TYPE 2 adds __START_AT/__END_AT, which take the data type of the SEQUENCE BY column. Here they hold LSNs. The current row has __END_AT IS NULL.
    • TRACK HISTORY ON segment, country: only these columns open a new version. An email change updates the current version in place, so email behaves as Type 1.
    Design consequence for the as-was join: with SEQUENCE BY lsn, the validity range is in LSNs, but orders carry a timestamp. Either sequence by the source commit time with the LSN as a tie-breaker, SEQUENCE BY STRUCT(changed_at, lsn) (then __START_AT.changed_at is a timestamp), or keep LSN sequencing and map versions to times in Gold. AUTO CDC also doesn't generate a surrogate key. Derive one, for example xxhash64(customer_id, __START_AT), in the Gold view. Requirements: AUTO CDC needs a serverless, Pro or Advanced pipeline, and it does not run as a plain notebook cell.

    B. Hand-written: the staged-union MERGE

    This is roughly what AUTO CDC saves you from writing. A single MERGE must both close the old version and insert the new one for the same key, but one source row can only drive one action. The trick is to stage each changed row twice: once with its real key (matches the current row and closes it) and once with a NULL merge key (can never match, so it gets inserted).

    MERGE INTO dim_customer t
USING (
  SELECT b.customer_id AS merge_key, b.* FROM cust_batch b          -- closes / updates / inserts new keys
  UNION ALL
  SELECT NULL AS merge_key, b.* FROM cust_batch b                   -- inserts the new version
  JOIN dim_customer d ON d.customer_id = b.customer_id AND d.is_current
  WHERE b.op <> 'D' AND b.lsn > d.lsn
    AND (NOT (b.segment <=> d.segment) OR NOT (b.country <=> d.country))
) s
ON t.customer_id = s.merge_key AND t.is_current
WHEN MATCHED AND s.lsn > t.lsn AND s.op = 'D' THEN
  UPDATE SET is_current = false, valid_to = s.changed_at
WHEN MATCHED AND s.lsn > t.lsn
     AND (NOT (s.segment <=> t.segment) OR NOT (s.country <=> t.country)) THEN
  UPDATE SET is_current = false, valid_to = s.changed_at            -- Type 2: close
WHEN MATCHED AND s.lsn > t.lsn THEN
  UPDATE SET email = s.email, lsn = s.lsn                           -- Type 1: in place
WHEN NOT MATCHED AND s.op <> 'D' THEN
  INSERT (customer_sk, customer_id, segment, country, email, lsn, valid_from, valid_to, is_current)
  VALUES (xxhash64(s.customer_id, s.changed_at), s.customer_id, s.segment, s.country,
          s.email, s.lsn, s.changed_at, NULL, true);
    • cust_batch must have one row per key (latest LSN in the batch, from a row_number() window, Gerald's DB4). Otherwise MERGE fails with multiple source rows matching one target row.
    • <=> is null-safe equality, so a change from NULL to a value still counts as a change.
    • The s.lsn > t.lsn guard makes the MERGE idempotent: re-running the same batch changes nothing.
    • A deterministic hash surrogate key (instead of an identity column) gives the same customer_sk if you rebuild the table from Bronze. Identity values would be renumbered.

    The fact: surrogate key as of order time, -1 when unknown

    gold.fact_order_line has the grain of order_items (one row per order line) and carries customer_sk, the key of the version that was valid when the order happened.

    CREATE OR REPLACE TABLE gold.fact_order_line AS
SELECT i.order_id, i.line_no, i.order_ts, i.sku, i.qty, i.line_amount,
       COALESCE(d.customer_sk, -1) AS customer_sk        -- unknown / late-arriving customer
FROM silver.order_items i
LEFT JOIN silver.dim_customer d
  ON  d.customer_id = i.customer_id
  AND i.order_ts >= d.valid_from
  AND (i.order_ts < d.valid_to OR d.valid_to IS NULL);   -- half-open range: exactly one version

    The dim also gets one explicit unknown member row (customer_sk = -1, segment 'Unknown'), so an inner join from fact to dim never drops revenue. Order 1004 belongs to C9, which isn't in the CDC feed yet, so it maps to -1 instead of disappearing.

    The SCD2 fan-out bug

    C1 has two versions (SMB/BR until 2026-10-12, then Enterprise/PT). Join on the business key alone and every C1 line matches both:

    -- WRONG: no current-row filter, no time range
SELECT SUM(i.line_amount) FROM order_items i
JOIN dim_customer d ON d.customer_id = i.customer_id;     -- 305, and C9's 30 is silently gone
    Join conditionWhat you getC1 + C2 revenue
    customer_id onlyFan-out: each C1 line × 2 versions(100 + 40) × 2 + 25 = 305
    customer_id + __END_AT IS NULL (or is_current)Correct row count, as-is attributes (today's segment)165 · Enterprise 140, SMB 25
    customer_id + time rangeCorrect row count, as-was attributes165 · SMB 125, Enterprise 40

    The wrong query has two bugs: C1's lines are doubled (280 instead of 140), and the inner join silently drops C9's 30 because C9 has no dim row. The correct total, with the -1 member, is 195. Both correct versions are legitimate. They answer different questions. In practice the as-was answer is stored in the fact as customer_sk, and the as-is answer comes from joining customer_sk → customer_id → the current row.

CREATE OR REPLACE TABLE orders_checked AS
SELECT *,
  CASE WHEN order_id IS NULL                               THEN 'null_order_id'
       WHEN items IS NULL OR size(items) = 0               THEN 'no_items'
       WHEN exists(items, i -> i.price <= 0 OR i.qty <= 0) THEN 'non_positive_amount'

FROM orders_raw;

CREATE OR REPLACE TABLE orders_quarantine AS
SELECT *, current_timestamp() AS quarantined_at FROM orders_checked WHERE dq_reason IS NOT NULL;

CREATE OR REPLACE TABLE orders AS
SELECT order_id, customer_id, order_ts FROM orders_checked WHERE dq_reason IS NULL;

CREATE OR REPLACE TABLE customers_cdc_quarantine AS
SELECT *, 'invalid_op' AS dq_reason FROM customers_cdc WHERE op NOT IN ('I', 'U', 'D');

SELECT dq_reason, COUNT(*) AS n FROM orders_quarantine GROUP BY dq_reason;   -- 2 rows: null_order_id, non_positive_amount

    Cell 4 · dim_customer SCD2 via staged-union MERGE (Python driving SQL)

    spark.sql("USE workspace.silver_lab")
spark.sql("""CREATE OR REPLACE TABLE dim_customer (
  customer_sk BIGINT, customer_id STRING, segment STRING, country STRING, email STRING,
  lsn BIGINT, valid_from TIMESTAMP, valid_to TIMESTAMP, is_current BOOLEAN)""")
spark.sql("""INSERT INTO dim_customer VALUES
  (-1, '-1', 'Unknown', 'Unknown', NULL, -1, TIMESTAMP'1900-01-01 00:00:00', NULL, true)""")

MERGE_SQL = """
MERGE INTO dim_customer t
USING (
  SELECT b.customer_id AS merge_key, b.* FROM cust_batch b
  UNION ALL
  SELECT NULL AS merge_key, b.* FROM cust_batch b
  JOIN dim_customer d ON d.customer_id = b.customer_id AND d.is_current
  WHERE b.op <> 'D' AND b.lsn > d.lsn
    AND (NOT (b.segment <=> d.segment) OR NOT (b.country <=> d.country))
) s
ON t.customer_id = s.merge_key AND t.is_current
WHEN MATCHED AND s.lsn > t.lsn AND s.op = 'D' THEN
  UPDATE SET is_current = false, valid_to = s.changed_at
WHEN MATCHED AND s.lsn > t.lsn AND (NOT (s.segment <=> t.segment) OR NOT (s.country <=> t.country)) THEN
  UPDATE SET is_current = false, valid_to = s.changed_at
WHEN MATCHED AND s.lsn > t.lsn THEN
  UPDATE SET email = s.email, lsn = s.lsn
WHEN NOT MATCHED AND s.op <> 'D' THEN
  INSERT (customer_sk, customer_id, segment, country, email, lsn, valid_from, valid_to, is_current)
  VALUES (xxhash64(s.customer_id, s.changed_at), s.customer_id, s.segment, s.country,
          s.email, s.lsn, s.changed_at, NULL, true)
"""

for batch in [1, 2, 2]:          # batch 2 twice = the re-run test
    spark.sql(f"""CREATE OR REPLACE TEMP VIEW cust_batch AS
      SELECT batch_id, customer_id, op, lsn, changed_at, segment, country, email FROM (
        SELECT *, row_number() OVER (PARTITION BY customer_id ORDER BY lsn DESC) AS rn
        FROM customers_cdc WHERE batch_id = {batch} AND op IN ('I', 'U', 'D'))
      WHERE rn = 1""")
    spark.sql(MERGE_SQL)

display(spark.sql("SELECT * FROM dim_customer ORDER BY customer_id, valid_from"))

    Cell 5 · Fact join + tests (SQL)

    %sql
USE workspace.silver_lab;
CREATE OR REPLACE TABLE fact_order_line AS
SELECT i.order_id, i.line_no, i.order_ts, i.sku, i.qty, i.line_amount,
       COALESCE(d.customer_sk, -1) AS customer_sk
FROM order_items i
LEFT JOIN dim_customer d
  ON d.customer_id = i.customer_id AND i.order_ts >= d.valid_from
 AND (i.order_ts < d.valid_to OR d.valid_to IS NULL);

-- As-was revenue by segment: SMB 125, Enterprise 40, Unknown 30
SELECT d.segment, SUM(f.line_amount) AS revenue
FROM fact_order_line f JOIN dim_customer d ON d.customer_sk = f.customer_sk
GROUP BY d.segment ORDER BY revenue DESC;

-- Tests: every value should be 0 (or the two sides equal)
SELECT
  (SELECT COUNT(*) - COUNT(DISTINCT order_id, line_no) FROM order_items)      AS dup_item_lines,
  (SELECT COUNT(*) - COUNT(DISTINCT order_id, line_no) FROM fact_order_line)  AS dup_fact_lines,
  (SELECT COUNT(*) FROM orders_raw)
    - (SELECT COUNT(*) FROM orders) - (SELECT COUNT(*) FROM orders_quarantine) AS unreconciled_orders,
  (SELECT COUNT(*) FROM order_items) - (SELECT COUNT(*) FROM fact_order_line) AS lost_fact_lines,
  (SELECT COUNT(*) FROM (SELECT customer_id FROM dim_customer
                         GROUP BY customer_id HAVING COUNT_IF(is_current) > 1)) AS multi_current;

    9 · Interview questions · ~5 min

    Answer out loud first, then reveal

    Senior US DE loops test whether you see these four topics as one design. Take 60–90 seconds per question.

    Q1 (design). "Design the Silver and Gold layers for orders and customers so revenue by customer segment is correct historically and stays correct when the pipeline re-runs."

    Strong answer: I start by stating the grain of every table: orders is one row per order, order_items one per line keyed on (order_id, line_no), order_payments one per payment, dim_customer one per customer version, and fact_order_line one per order line. Bronze to Silver goes through a quality gate where each rule has an explicit action. Rows the business cares about go to quarantine with a reason, and I reconcile bronze = silver + quarantine on every run. segment and country are SCD2 because we report history on them. Email is Type 1. The dimension is sequenced by a source ordering column (the LSN), so out-of-order CDC can't corrupt history. On Databricks that's AUTO CDC with SEQUENCE BY and TRACK HISTORY ON, or a guarded MERGE. The fact stores the surrogate key of the version valid at order time, with -1 for unknown customers. Re-runs are idempotent because everything is MERGE or AUTO CDC, never a blind append. Tests check grain uniqueness and at most one current row per key. Finally I make the as-was vs as-is choice explicit and offer both: as-was through the fact's surrogate key, as-is through the current row.

    Q2 (debugging). "Revenue in the dashboard doubled after someone added the payments table to the query. What happened and how do you prevent it?"

    Strong answer: That's join fan-out. Items and payments are both many sides of an order. Joining both to the order produces items × payments rows per order, so an order with 2 lines and 2 payments is counted twice. The fix is to aggregate each many side to the parent grain (order) before joining, or to keep payments out of a line-grain fact entirely. To prevent it: every table has a declared grain, documented as an informational PK in Unity Catalog. A uniqueness test on that key runs in CI and in the Job. A row-count/revenue reconciliation between the fact and its source table would have failed the moment the row count grew. I'd also make sure reviewers ask "what's the grain after this join?" in code review.

    Q3 (behavioral, tech lead). "Tell me about a time bad data reached a report."

    Strong answer shape (use a real story): Situation: one sentence on the report and who noticed. Gap: name the missing gate exactly, for example "a nullable key with no rule, so rows were silently dropped by an inner join". Fix: what you did that day (backfill from Bronze, which works because Bronze is append-only and replayable) and how you told stakeholders. Standard: what you put in place for the team, not just that pipeline: a per-rule action policy (warn/drop/fail/quarantine with an owner for each quarantine table), grain tests required on every new table, and reconciliation counts on the run dashboard. Close with a measurable result, such as "no repeat incidents in six months" or "time to detect went from days to one run".

    Q4 (trade-off). "Why not make every dimension column Type 2, just to be safe?"

    Strong answer: Because history isn't free and it isn't always correct. Every tracked change creates a version, so a frequently updated column (last login, email, a counter) explodes the dim's row count and makes as-was joins slower and harder to reason about. It also changes meaning: if email were Type 2, a corrected typo would look like a "new customer state". I pick Type 2 per attribute: only what the business reports on historically (segment, country, price tier). Everything else is Type 1. With AUTO CDC that's exactly TRACK HISTORY ON segment, country. Anything else is a conversation with the data's consumers, not a default.

    Q5 (detail). "Identity column or hash for the surrogate key?"

    Strong answer: Both work, with different trade-offs. A Delta identity column gives compact, unique BIGINTs but assigns new values if you rebuild the table, so every fact has to be rebuilt with it. A deterministic hash of the business key and version start (for example xxhash64(customer_id, valid_from)) is reproducible across rebuilds and environments, which fits a pipeline that's meant to be re-run from Bronze. Its costs are a tiny collision risk (tested with a uniqueness check) and wider keys if you use SHA-based hashes. Either way, -1 is reserved for the unknown member.
