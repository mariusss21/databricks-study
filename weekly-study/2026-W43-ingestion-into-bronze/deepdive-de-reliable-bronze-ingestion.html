    Four questions every Bronze source has to answer

    This week brought four DE pills (Mon–Thu). Each one looks like a separate topic. They aren't. They are the four questions you answer, out loud, for every source you bring into Bronze:

    1. How do I detect change? → CDC (log, query, or trigger based) or a high-water mark when you only have an API. DE1 · DE4
    2. How do I avoid losing or duplicating it? → delivery semantics: at-least-once transport + an idempotent sink + checkpoints. DE2
    3. How do I survive the source changing shape? → tolerant Bronze, strict Silver, Auto Loader evolution and _rescued_data. DE3
    4. How do I recover and replay? → append-only raw data, retained landing files, chunked idempotent backfills. DE4

    You'll follow one realistic pipeline the whole time: an e-commerce company with a Postgres orders table (log-based CDC) and a payments SaaS REST API (watermark pull). Then you'll break it four ways and watch what happens.

    Recap · 4 topics · ~8 min

    The four pills on one screen

    1 · CDC fundamentals DE1 Mon

    Log-based (Postgres WAL via logical replication, MySQL binlog): catches deletes and every intermediate change, light on the source, the gold standard (Debezium, Lakeflow Connect, Fivetran). Query-based (updated_at > mark): simple, misses hard deletes, squashes updates between polls. Trigger-based: accurate, but adds write overhead DBAs dislike.

    A Debezium event carries op (c/u/d/r), before, after, source.lsn, ts_ms. The LSN is your ordering key. Bronze keeps every event as it arrived, deletes included.

    2 · Incremental extraction DE4 Thu

    High-water mark: store the largest updated_at you've loaded; next run asks for newer rows. Traps: ties and late commits (fix: overlap window + dedup), invisible deletes, an updated_at not set by every writer.

    APIs: cursor/keyset pagination beats offset (offsets shift mid-read). On 429 honour Retry-After, back off with jitter. Backfills: chunked, idempotent, same code as the daily run with different parameters.

    3 · Delivery semantics DE2 Tue

    At-most-once (may lose), at-least-once (may duplicate, the normal case for Kafka, Debezium, APIs), exactly-once (an end-to-end property: replayable source + tracked progress + transactional or idempotent sink).

    Databricks: checkpoints + Delta sink = exactly-once into Delta; Auto Loader tracks files; foreachBatch needs txnAppId/txnVersion; Trigger.AvailableNow = streaming semantics at batch cost.

    4 · Schema drift + contracts DE3 Wed

    Tolerant Bronze, strict Silver. Bronze must never lose a field or stop for good because of a surprise; Silver enforces the contract (explicit schema, expectations) and fails loudly.

    Auto Loader: schemaLocation, schemaEvolutionMode (addNewColumns stops once then continues; rescue never stops), _rescued_data for type/case mismatches and unknown fields. Delta: mergeSchema, type widening. VARIANT for semi-structured payloads.

    The one sentence that ties them together"Bronze is an append-only, replayable record of what the source told us, at-least-once, with nothing silently lost; correctness (dedup, current state, contracts) is earned in Silver."
    Check: the orders team deletes cancelled orders from Postgres with a hard DELETE. Which capture method sees those deletes without extra work?
    Check: a payments API offers ?page=N and ?cursor=…. Rows get updated while you paginate. Why prefer the cursor?

    End-to-end walkthrough · ~10 min

    Ingest an e-commerce company into Bronze

    Source A is Postgres orders (we can read its log). Source B is a payments SaaS API (we can't). Same destination rules for both: raw, append-only, replayable. Production names use catalog prod; the lab later uses workspace.dd_de.

    Step 1: What a change looks like when you can read the log

    Debezium's Postgres connector reads the WAL through a logical replication slot and emits one event per row change. With the JSON converter and schemas enabled, the event body sits under payload:

    Debezium event (update of order 1003, trimmed)
    {
  "payload": {
    "op": "u",
    "before": {"order_id": 1003, "status": "PENDING", "amount": 310.00},
    "after":  {"order_id": 1003, "status": "PAID",    "amount": 310.00},
    "source": {"connector": "postgresql", "db": "shop", "schema": "public",
               "table": "orders", "lsn": 24023128, "txId": 9871},
    "ts_ms": 1761210421337
  }
}
    • op: c create, u update, d delete (only before is set), r snapshot read.
    • source.lsn: position in the log. This is the ordering and dedup key next week, so Bronze must keep it.
    • After a delete, Debezium can also emit a tombstone (null value) for Kafka log compaction. It carries no data; filter it.
    Question 1 answered for Source AChange detection is the database's own log: deletes and intermediate updates included, near-zero load on the source. The price: a replication slot to monitor. If the consumer falls behind, the WAL grows on the primary, and if you ever lose the slot you need a re-snapshot.

    Step 2: Land the raw events append-only

    Build: Debezium → Kafka → Structured Streaming → prod.bronze.orders_cdc. Kafka is the replayable source (offsets + retention), the checkpoint tracks offsets, the Delta sink is transactional: exactly-once into Bronze, at-least-once from Postgres (Debezium can redeliver after a crash).

    PySpark · build option (illustration)
    from pyspark.sql import functions as F

events = (spark.readStream.format("kafka")
    .option("kafka.bootstrap.servers", dbutils.secrets.get("cdc", "bootstrap"))
    .option("subscribe", "shop.public.orders")      # Debezium topic: prefix.schema.table
    .option("startingOffsets", "earliest")
    .load()
    .where("value IS NOT NULL")                     # drop tombstones
    .select(
        F.expr("parse_json(CAST(value AS STRING))").alias("event"),   # VARIANT: keep the whole envelope
        "topic", "partition", "offset",
        F.col("timestamp").alias("kafka_ts"))
    .select("*",
        F.expr("event:payload.op::string").alias("op"),
        F.expr("event:payload.source.lsn::bigint").alias("source_lsn"),
        F.expr("event:payload.ts_ms::bigint").alias("source_ts_ms"),
        F.current_timestamp().alias("_ingested_at")))

(events.writeStream
    .option("checkpointLocation", "/Volumes/prod/raw/ops/checkpoints/orders_cdc")
    .trigger(availableNow=True)                     # schedule it; pay only while it runs
    .toTable("prod.bronze.orders_cdc"))

    Why VARIANT for the envelope: the before/after images change shape whenever someone runs ALTER TABLE orders ADD COLUMN. VARIANT keeps Bronze tolerant (question 3) without a schema decision on day one, and you still promote op, source_lsn and ts_ms to real columns because Silver will sort and filter on them.

    Buy: Lakeflow Connect's managed PostgreSQL connector does the snapshot + incremental CDC, retries and schema changes for you, and lands into streaming tables. In an interview, say both: "I'd start with the managed connector, and only build Debezium + Kafka if we need fan-out to other consumers or a source it doesn't cover."

    Step 3: Source B has no log, so you pull with a high-water mark

    The payments API exposes GET /v1/payments?updated_since=…&cursor=…&limit=100. The extractor's loop answers question 1 the hard way:

    Python · the extractor's shape
    since  = read_mark("payments_api") - timedelta(minutes=10)   # overlap window: ties + late commits
cursor = None
while True:
    resp = get("/v1/payments", updated_since=since, cursor=cursor, limit=100)
    if resp.status in (429, 503):                             # throttled: honour the server
        sleep(float(resp.headers.get("Retry-After", backoff())) + jitter())
        continue
    resp.raise_for_status()
    write_page_to_volume(resp.json()["data"], run_id, page_no)  # raw JSON, unique file name
    cursor = resp.json().get("next_cursor")                  # keyset, not page numbers
    if not cursor:
        break
# NOTE: the mark is NOT touched here. Pages are landed, not yet committed to Bronze.

    The overlap window costs duplicates

    Every run re-reads the last 10 minutes on purpose. You trade guaranteed duplicates for not missing a row that committed late or shared a timestamp with the mark. That trade only works because Bronze is append-only and Silver dedups.

    Deletes are still invisible

    A payment deleted on the SaaS side never appears in updated_since. Ask for a soft-delete flag or an events endpoint, or schedule a periodic full-key reconciliation. Say this in the interview before they ask.

    Step 4: Auto Loader commits the pages; only then does the mark move

    PySpark · pages → bronze.payments_raw
    raw = (spark.readStream.format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", "/Volumes/prod/raw/ops/schemas/payments_raw")
    .option("cloudFiles.inferColumnTypes", "true")
    .option("cloudFiles.schemaHints", "amount DECIMAL(10,2), updated_at TIMESTAMP")
    .option("cloudFiles.schemaEvolutionMode", "addNewColumns")
    .load("/Volumes/prod/raw/landing/payments/"))

(raw.withColumn("_source_file", F.col("_metadata.file_path"))
    .withColumn("_ingested_at", F.current_timestamp())
    .writeStream
    .option("checkpointLocation", "/Volumes/prod/raw/ops/checkpoints/payments_raw")
    .option("mergeSchema", "true")
    .trigger(availableNow=True)
    .toTable("prod.bronze.payments_raw")
    .awaitTermination())

# Only after the commit: advance the mark from what Bronze actually holds
spark.sql("""
  UPDATE prod.ops.ingest_marks
  SET last_mark = greatest(last_mark, (SELECT max(updated_at) FROM prod.bronze.payments_raw)),
      updated_at = current_timestamp()
  WHERE source = 'payments_api'""")
    1. Land raw pages (durable, unique names, never overwritten).
    2. Commit them to Bronze (checkpointed: each file exactly once).
    3. Advance the mark from the committed data, never from what you intended to write. greatest() stops it ever moving backwards.

    The lab computes the new mark in Python and passes a literal, which works the same everywhere; the subquery form above is the compact version.

            The pattern behind all fourEvery failure ends in either duplicates (recoverable, by design) or silent loss (unacceptable). Good Bronze design converts every failure mode into the first kind: commit before advancing, keep the landing files, never reuse a txnAppId with a new checkpoint, rescue instead of drop, make chunks idempotent.

            dbt's place, in one line

            "Fivetran or Airbyte do the EL, dbt does the T." dbt never touches the source system; its sources block is where you declare the raw tables, test them and check freshness. That's the closest thing to a data contract on Bronze in that stack.

            Buy vs build for 200+ sources

            Buy (Lakeflow Connect, Fivetran, Airbyte) for the standard SaaS and databases: someone else maintains cursors, deletes, rate limits and API changes. Build (Auto Loader, custom extractors, PySpark data sources) for the long tail, unusual APIs, or when per-row pricing gets expensive at volume. Your code factory for scrapers is a "build" answer to a source no vendor covers.

            A fake payments API and the extractor

            Python
            # cell 2 (Python): config + a fake payments API with ties, keyset cursor and 429s
import json, time, random, uuid
from datetime import datetime, timedelta, timezone

spark.conf.set("spark.sql.session.timeZone", "UTC")   # marks and API times are UTC

CAT, SCH    = "workspace", "dd_de"
LANDING     = f"/Volumes/{CAT}/{SCH}/landing/payments"
OPS         = f"/Volumes/{CAT}/{SCH}/ops"
BRONZE      = f"{CAT}.{SCH}.payments_raw"
MARKS       = f"{CAT}.{SCH}.ingest_marks"
OVERLAP_MIN = 10

T0 = datetime(2026, 10, 22, 9, 0, 0)
def iso(dt):
    return dt.strftime("%Y-%m-%dT%H:%M:%SZ")

# 10 payments; pairs share an updated_at (ties!): P-002/P-003 at 09:05 ... P-010 at 09:25
API_ROWS = [{"payment_id": f"P-{i:03d}", "order_id": 1000 + i, "amount": round(50 + 7.5 * i, 2),
             "status": "CAPTURED", "updated_at": iso(T0 + timedelta(minutes=5 * (i // 2)))}
            for i in range(1, 11)]

CALLS = {"n": 0}
def fake_api_get(updated_since, cursor=None, limit=4):
    """GET /v1/payments?updated_since=...&cursor=...  -> (status, headers, body)"""
    CALLS["n"] += 1
    if CALLS["n"] % 3 == 0:                                   # every 3rd call is throttled
        return 429, {"Retry-After": "2"}, None
    rows = sorted((r for r in API_ROWS if r["updated_at"] >= updated_since),   # inclusive
                  key=lambda r: (r["updated_at"], r["payment_id"]))
    if cursor:                                                 # keyset: resume after the last row seen
        cu, cid = cursor.split("|")
        rows = [r for r in rows if (r["updated_at"], r["payment_id"]) > (cu, cid)]
    page = rows[:limit]
    nxt = f'{page[-1]["updated_at"]}|{page[-1]["payment_id"]}' if len(rows) > limit else None
    return 200, {}, {"data": page, "next_cursor": nxt}

def get_with_backoff(since, cursor, max_tries=6):
    for attempt in range(max_tries):
        status, headers, body = fake_api_get(since, cursor)
        if status == 200:
            return body
        wait = float(headers.get("Retry-After", 2 ** attempt)) + random.uniform(0, 0.5)   # honour + jitter
        print(f"  HTTP {status}: sleeping {wait:.1f}s (attempt {attempt + 1})")
        time.sleep(wait)
    raise RuntimeError("API still throttling after retries")

def extract(since):
    """Pull every page since `since` and land each page as a new, uniquely named JSON-lines file."""
    run_id = datetime.now(timezone.utc).strftime("%Y%m%dT%H%M%S") + "_" + uuid.uuid4().hex[:6]
    cursor, page_no, n = None, 0, 0
    while True:
        body = get_with_backoff(since, cursor)
        if body["data"]:
            page_no += 1
            dbutils.fs.put(f"{LANDING}/{run_id}_page_{page_no:03d}.json",
                           "\n".join(json.dumps(r) for r in body["data"]), overwrite=False)
            n += len(body["data"])
        cursor = body["next_cursor"]
        if not cursor:
            break
    print(f"extract since {since}: {n} rows in {page_no} file(s), run {run_id}")
    return n

            Read the API before you run anything: the filter is inclusive (>=), pages hold 4 rows, the cursor is updated_at|payment_id, and every third call gets a 429. Each page lands as a new file, never overwriting one, so the landing volume becomes your replay log.

            Land → commit → advance, then run 1

            Python
            # cell 3 (Python): mark -> Bronze (Auto Loader) -> advance mark AFTER commit
from pyspark.sql import functions as F

def read_since():
    return spark.sql(f"""
        SELECT date_format(last_mark - INTERVAL {OVERLAP_MIN} MINUTES, "yyyy-MM-dd'T'HH:mm:ss'Z'") AS s
        FROM {MARKS} WHERE source = 'payments_api'""").first()["s"]

def load_bronze():
    raw = (spark.readStream.format("cloudFiles")
        .option("cloudFiles.format", "json")
        .option("cloudFiles.schemaLocation", f"{OPS}/schemas/payments_raw")
        .option("cloudFiles.inferColumnTypes", "true")
        .option("cloudFiles.schemaHints", "amount DECIMAL(10,2), updated_at TIMESTAMP")
        .option("cloudFiles.schemaEvolutionMode", "addNewColumns")
        .load(LANDING))
    q = (raw.withColumn("_source_file", F.col("_metadata.file_path"))
            .withColumn("_ingested_at", F.current_timestamp())
            .withColumn("_chunk", F.lit("incremental"))
            .writeStream
            .option("checkpointLocation", f"{OPS}/checkpoints/payments_raw")
            .option("mergeSchema", "true")
            .trigger(availableNow=True)
            .toTable(BRONZE))
    q.awaitTermination()
    print("bronze rows:", spark.table(BRONZE).count())

def advance_mark():
    new_mark = spark.sql(f"""
        SELECT date_format(max(updated_at), 'yyyy-MM-dd HH:mm:ss') AS m
        FROM {BRONZE} WHERE _chunk = 'incremental'""").first()["m"]
    spark.sql(f"""
        UPDATE {MARKS}
        SET last_mark = greatest(last_mark, TIMESTAMP '{new_mark}'), updated_at = current_timestamp()
        WHERE source = 'payments_api'""")
    print("mark is now", spark.table(MARKS).where("source = 'payments_api'").first()["last_mark"])

def run_cycle(advance=True):
    since = read_since()
    extract(since)          # 1. land
    load_bronze()           # 2. commit
    if advance:
        advance_mark()      # 3. advance, only after the commit
    else:
        print("💥 simulated crash: pages committed to Bronze, mark NOT advanced")

run_cycle()                 # run 1: expect 10 rows, mark 2026-10-22 09:25:00

            Expect: one "HTTP 429: sleeping…" line, 10 rows in 3 files, bronze rows: 10, mark 2026-10-22 09:25:00. Run load_bronze() once more by itself: still 10 rows (the checkpoint already knows those files).

            The source changes, the job crashes (scenario a), the retry recovers

    API_ROWS.append({"payment_id": "P-011", "order_id": 1011, "amount": 99.90,   # late commit:
                     "status": "CAPTURED", "updated_at": iso(T0 + timedelta(minutes=22))})  # 09:22 < mark!

            Expect: run 2 extracts 7 rows (17 total) and leaves the mark at 09:25. Run 3 re-reads the same window, +7 (24 total), and the mark moves to 09:40.

            Why the overlap matteredP-011 committed late with updated_at = 09:22, which is before the 09:25 mark. With OVERLAP_MIN = 0, run 2 would have asked for >= 09:25, got only P-003 and P-010, and P-011 would be lost for good. The overlap traded 5 duplicates per run for not losing that row.

            Dedup proof: duplicates are deterministic

            SQL
            -- cell 5 (%sql): duplicates are expected in Bronze; prove they're deterministic
SELECT count(*)                                 AS bronze_rows,      -- 24
       count(DISTINCT payment_id, updated_at)   AS distinct_versions,-- 12
       count(DISTINCT payment_id)               AS payments          -- 11
FROM workspace.dd_de.payments_raw
WHERE _chunk = 'incremental';

-- one row per (payment_id, updated_at) version: the shape Silver will start from
SELECT payment_id, status, amount, updated_at, _source_file
FROM workspace.dd_de.payments_raw
WHERE _chunk = 'incremental'
QUALIFY row_number() OVER (PARTITION BY payment_id, updated_at ORDER BY _ingested_at) = 1
ORDER BY payment_id, updated_at;

            Expect: 24 / 12 / 11, and the second query returns 12 rows (P-003 appears twice: CAPTURED at 09:05 and REFUNDED at 09:40). Picking the latest version per payment is a Silver job for next week; here you only show the duplicates are harmless.

            Interview practice · ~10 min

            Senior-style questions (answer out loud first)

            Give yourself ~2 minutes per question, in English, then reveal. Senior framing: failure modes first, then cost and ownership, then data contracts with the producer teams.

            1. "We have 50 tables in an OLTP Postgres and 20 SaaS APIs. Design ingestion into the lakehouse."

            Clarify first: freshness SLA per source, volumes and change rates, whether deletes matter, who owns each source, budget, and whether other teams need the change stream too.

            Postgres (50 tables): log-based CDC, never polling 50 tables: it catches deletes and doesn't load the primary. I'd start with a managed connector (Lakeflow Connect's PostgreSQL connector, or Fivetran) and only build Debezium + Kafka if we need fan-out to other consumers or sub-minute latency. I'd ask the DBAs for a replica or replication slot, and monitor slot lag, because a stuck consumer makes the WAL grow on the primary. Bronze gets one append-only table per source table with op, the LSN and the commit timestamp.

            SaaS APIs (20): buy for the common ones (Salesforce, Stripe, HubSpot…); build the rest with one shared extractor framework: a high-water mark in a Delta control table, an overlap window, cursor pagination, 429 handling with Retry-After and jitter, raw pages landed in a volume, Auto Loader into Bronze, and the mark advanced only after commit. Plus a periodic reconciliation for sources that hide deletes.

            Delivery and drift: everything is at-least-once, so Bronze is append-only with dedup keys and Silver dedups. Bronze is tolerant (addNewColumns, _rescued_data, VARIANT); Silver enforces contracts with expectations.

            Operations: Lakeflow Jobs with retries and alerts, availableNow on a schedule to control cost, retained landing data for replay, parameterized chunked backfills, freshness and row-count monitoring per source, and named owners and data contracts with the producer teams: schema changes announced, not discovered.

            Shape to remember: clarify → split by source type → buy vs build → delivery + drift → operate.

            2. "Exactly-once: is it real?"

            "Yes, but only as an end-to-end property of a specific pipeline, not of a transport. Networks and producers retry, so delivery is at-least-once in practice. You get effectively exactly-once results when three things line up: a replayable source (Kafka offsets, files on storage), tracked progress (a checkpoint), and a transactional or idempotent sink."

            "On Databricks, Structured Streaming with a checkpoint writing to Delta gives exactly-once into that table. Auto Loader tracks each file once. With foreachBatch you add idempotency yourself with txnAppId/txnVersion, or a MERGE keyed on the record. But the guarantee stops at the boundary: if Debezium redelivers after a crash, Bronze correctly stores the duplicate, and Silver removes it by key and LSN. And if someone deletes the checkpoint, the guarantee is gone: you replay everything, or with a reused txnAppId you silently skip data."

            "So my design rule is: assume at-least-once everywhere and make every write idempotent."

            3. "Your watermark-based pipeline is missing rows. How do you debug it?"

            Check the usual suspects in order. (1) Mark advanced before the write committed, then a crash: look at the control table history (DESCRIBE HISTORY) against the Bronze commits. (2) Ties and late commits: a strict > filter or no overlap drops rows sharing the mark's timestamp, or transactions that committed later with an older updated_at. (3) Time zones: the mark stored in local time, compared with a UTC column. (4) Untrusted column: some writers (bulk jobs, triggers off) don't touch updated_at. (5) Offset pagination shifting during the read. (6) Deletes, which a watermark never sees.

            Prove it by comparing keys: a full key extract from the source vs Bronze for a window. Then fix the cause, and backfill the gap with a chunked, idempotent run.

            4. "Someone deleted a streaming checkpoint in production. What happens, and what do you do?"

            On restart the stream has no memory: Auto Loader re-reads every file still in the source path and Bronze gets a full duplicate copy. If the sink is foreachBatch with txnAppId, it's worse: batch IDs restart at 0, Delta treats them as already written, and new data is silently skipped. That's why the docs say a new checkpoint needs a new txnAppId.

            Recovery: stop the job. Either rebuild Bronze from retained landing data into a new table with a fresh checkpoint and swap it in, or restore the table to the version before the replay (time travel) and restart with includeExistingFiles = false plus a targeted backfill for the gap. Prevention: checkpoints in a dedicated volume that only the job's service principal can write, no lifecycle rules on it, and a runbook.

            Phrases that sound senior

            "The trade-off here is duplicates versus missed rows. I'll take duplicates, because dedup is cheap and a missing row is invisible."

            "I'd start with a managed connector, and only move to Debezium and Kafka if other teams need the change stream."

            "The failure mode I'm designing for is a crash between the write and the mark update."

            "Before I pick a tool, I'd want to know the freshness SLA and whether deletes matter."

            English traps to avoid

            Say "at-least-once" and "exactly-once" (hyphenated), not "one time only".

            "The data landed / was ingested", not "the data entered".

            "We backfill three months", not "we reprocess the past".

            Say "it depends on X", then commit to an answer for the stated X. Don't stop at "it depends".
