    W46 in three cards: build it gated, run it, debug it from evidence

    Welcome back. This closes W46 ("Gold objects and Lakeflow Jobs") and its exam pills. Today's lesson has one thread: one daily revenue Gold table that's built behind a quality gate, run by a Job on the right trigger, and fixed from evidence when a run goes red or slow.

    Topic 1 · Gold object + gate

    Pick the object on purpose, then gate what goes into it.

    • Table vs view vs materialized view vs streaming table in Unity Catalog. Plus grants: consumers get SELECT, not your Silver.
    • Constraints (NOT NULL, CHECK): a violating write fails the whole transaction.
    • Expectations in pipelines: warn keeps bad rows, drop removes them, fail stops the update. A quarantine table keeps them for review.
    • try_cast bad strings into NULLs, then count the NULLs as a quality metric (pill 11-10).
    • Declare Gold's grain and check it against source counts (pill 11-14).
    Topic 2 · Lakeflow Jobs

    A DAG of tasks, started by the trigger that matches how data arrives.

    • Task DAG, dependencies, run if, retries, task values, for each and if/else.
    • Triggers: schedule vs file arrival vs table update.
    • Repair run: re-runs only unsuccessful tasks and their dependents.
    • Pill 11-09: run history is your baseline, not a single green check.
    • Pill 11-10: the Jobs UI shows status, the task DAG (which upstream task blocked the rest), run time and failure rate.
    Topic 3 · Slow or failing runs

    Find the cause in the Spark UI before you touch hardware.

    • Skew (11-11): most tasks finish fast, one runs for minutes, and max shuffle read is far above the median.
    • Skewed groupBy (11-12): salt the key. AQE skew handling only splits joins, and more executors leave the one huge task alone.
    • Spill (11-13) shows in the stage metrics, not in the job's total time.
    • Liquid clustering CLUSTER BY (11-14) and predictive optimization for UC managed tables (11-15).
    • Check shuffle, spill and skew before adding executors, and keep a tuning log (tech pill 11-15).
    Exam trap to lock in now. Sample question 1 in the current exam guide (August 2026) is a groupBy on customer_id with one giant task. The answer is D: salt the key. It is not "enable AQE" (AQE's skew handling splits skewed joins, not aggregations) and not "add executors" (the giant task still runs on one core).

    Topic 1 · The quality gate

    Three layers, each catching something different

    LayerWhat it catchesWhat happens to bad rows
    try_cast(amount_raw AS DECIMAL(10,2)) in Silver, then count the NULLsStrings like 'n/a' that aren't amounts. Serverless runs with ANSI mode on, so a plain CAST would fail the whole job.They become NULL. The NULL count is a metric (200 of 200,000 = 0.10% in the hands-on). Rows with a NULL amount go to silver_orders_quarantine.
    Constraints on Gold: NOT NULL columns, CHECK (revenue_brl >= 0)Anything that should never be written.The whole write fails. No partial table.
    Gate task: null % ≤ 0.5, grain unique, Σ orders in Gold = valid Silver rowsAggregate problems that no single row shows: duplicated keys, missing data, a fan-out.Sets task value gate = pass/fail. The Job publishes or holds.

    In a pipeline (W47) you'd write the row-level rule as an expectation instead: EXPECT (warn) writes bad rows and records metrics, ON VIOLATION DROP ROW drops them and counts them, and ON VIOLATION FAIL UPDATE stops the update. None of the three keeps the bad rows for review, which is why a quarantine table exists.

    35,000 Gold rows = 35,000 distinct keys Σ orders 199,800 = valid Silver rows

    Topic 2 · Orchestrate it

    Which trigger? It depends on how the data arrives

    TriggerStarts a run when…Pick it when…
    ScheduleThe clock says so (cron + time zone).Data lands on a known clock, or the SLA is a fixed time and reruns are cheap.
    File arrivalNew files appear in a UC volume or external location (best-effort check about every minute).The upstream is a file drop and nothing writes a table yet. Only new files trigger. Overwriting a file with the same name doesn't.
    Table updateMonitored UC tables change (any or all of them).Our case: another team's job writes bronze_orders at irregular times. You run when data is ready without knowing their process.

    Two advanced options shape the table-update trigger: wait after last change (each new update resets the timer, so a batch of loads gives one run) and minimum time between triggers (a cooldown after a run completes). The job's Run as principal needs SELECT on the monitored table.

    TaskDepends onWhy it's set up this way
    build_silver(root)try_cast, quarantine. Retries are safe because it overwrites.
    build_goldbuild_silver1 retry, 45-minute timeout. Overwrites its slice, so a retry or repair can't double revenue.
    quality_gatebuild_goldNo retries: bad data doesn't fix itself. Sets the task value gate.
    gate_passed (if/else)quality_gate{{tasks.quality_gate.values.gate}} == "pass"
    publish / hold_and_alertgate_passed = true / falseThe branch that isn't taken is marked Excluded (skipped).
    log_runboth branches, run if: All doneAlways appends duration and gate metrics, whatever happened upstream. This is your tuning log and baseline.

    You'd use for each to loop a task over a list, for example rebuilding several dates in a backfill. This Gold table doesn't need one.

    Topic 3 → 2 · Fix the cause, then repair the run

    Every option on the table, and which one hits the cause

    OptionDoes it fix this stage?
    Add executors / bigger computeNo. The giant task still runs alone on one core while the new cores sit idle (and on serverless you don't size workers anyway).
    Enable or tune AQE skew joinNo. AQE splits skewed partitions of sort-merge and shuffle hash joins. This is an aggregation. (AQE is already on by default.)
    Raise spark.sql.shuffle.partitionsNo. However many partitions there are, one key still lands in one of them.
    Salt the key (two-stage aggregation)Yes. Add salt = pmod(hash(order_id), 8), aggregate by (customer_id, salt), then aggregate the partials by customer_id. c_0000's work spreads over 8 tasks, which also ends the spill. Same result, exactly. This is exam sample Q1, answer D.
    CLUSTER BY (order_date, customer_id) on GoldNot for this stage. It helps readers: rows with similar keys sit in the same files, so dashboard filters skip files (pill 11-14). Use it when the skew comes from how a stored table is laid out.
    Predictive optimizationNot for this stage either. It replaces the old nightly OPTIMIZE + VACUUM maintenance job: Databricks runs OPTIMIZE, VACUUM and ANALYZE on eligible UC managed tables (pill 11-15). External tables aren't eligible.

    Repair, don't rerun. Deploy the salted notebook, open the failed 11-14 run and click Repair run. It re-runs only the unsuccessful tasks and their dependents (build_gold → quality_gate → gate_passed → publish, plus log_run). build_silver succeeded, so it isn't re-run. Repaired tasks use the current task settings and code, and you can override parameters in the dialog. This is safe only because build_gold overwrites its output: Jobs doesn't make a task idempotent for you. The run's duration then counts from the first attempt to the end of the repair.

    Build the gated Gold table, prove the grain, salt the hot key

    Create a notebook, attach serverless, set the default language to SQL, and paste one cell at a time (Python cells start with %python). Everything lands in workspace.dd_w46_db. Cell 1 recreates the data, so running from the top always starts fresh. Expected results are in the comments.

    Setup: Bronze with a hot customer and some bad amounts

    -- Cell 1 (SQL): 200,000 orders; c_0000 (the new reseller) gets 60% of them
USE CATALOG workspace;
CREATE SCHEMA IF NOT EXISTS dd_w46_db;
USE SCHEMA dd_w46_db;

CREATE OR REPLACE TABLE bronze_orders AS
SELECT
  concat('o', id)                                                     AS order_id,
  CASE WHEN id % 10 < 6 THEN 'c_0000'
       ELSE concat('c_', lpad(CAST(1 + id % 4999 AS STRING), 4, '0')) END AS customer_id,
  date_add(DATE'2026-11-09', CAST(id % 7 AS INT))                     AS order_date,
  CASE WHEN id % 1000 = 999 THEN 'n/a'                                 -- 200 bad strings
       ELSE concat(CAST(id % 200 + 10 AS STRING), '.50') END          AS amount_raw
FROM range(200000);

SELECT count(*) AS bronze_rows, count(DISTINCT customer_id) AS customers FROM bronze_orders;
-- 200000 | 5000

    Gate layer 1: try_cast, then count the NULLs

    -- Cell 2 (SQL): why try_cast. Serverless has ANSI mode on.
-- SELECT CAST('n/a' AS DECIMAL(10,2));        -- uncomment to see it fail (invalid cast error)
SELECT try_cast('n/a' AS DECIMAL(10,2)) AS becomes_null;
-- NULL
    -- Cell 3 (SQL): Silver with typed amount + the null-count quality metric
CREATE OR REPLACE TABLE silver_orders AS
SELECT order_id, customer_id, order_date,
       try_cast(amount_raw AS DECIMAL(10,2)) AS amount,
       amount_raw
FROM bronze_orders;

SELECT count(*)                                                  AS total_rows,
       count(*) - count(amount)                                  AS amount_nulls,
       round(100.0 * (count(*) - count(amount)) / count(*), 2)   AS null_pct
FROM silver_orders;
-- 200000 | 200 | 0.10
    -- Cell 4 (SQL): quarantine instead of silently dropping
CREATE OR REPLACE TABLE silver_orders_quarantine AS
SELECT *, 'amount not castable' AS reason, current_timestamp() AS quarantined_at
FROM silver_orders
WHERE amount IS NULL;

SELECT count(*) AS quarantined, min(amount_raw) AS sample_value FROM silver_orders_quarantine;
-- 200 | n/a

    Gate layer 2: a Gold table with a declared grain, constraints and clustering

    -- Cell 5 (SQL): create, constrain, load
CREATE OR REPLACE TABLE gold_daily_customer_revenue (
  order_date  DATE          NOT NULL,
  customer_id STRING        NOT NULL,
  orders      BIGINT        NOT NULL,
  revenue_brl DECIMAL(18,2) NOT NULL
) CLUSTER BY (order_date, customer_id);

COMMENT ON TABLE gold_daily_customer_revenue IS
  'Grain: one row per (order_date, customer_id). Excludes rows in silver_orders_quarantine.';

ALTER TABLE gold_daily_customer_revenue
  ADD CONSTRAINT revenue_non_negative CHECK (revenue_brl >= 0);

INSERT OVERWRITE TABLE gold_daily_customer_revenue
SELECT order_date, customer_id,
       count(*)                            AS orders,
       CAST(sum(amount) AS DECIMAL(18,2))  AS revenue_brl
FROM silver_orders
WHERE amount IS NOT NULL
GROUP BY order_date, customer_id;
-- num_affected_rows / num_inserted_rows: 35000  (5,000 customers × 7 days)
    -- Cell 6 (SQL): grain check
SELECT count(*)                                AS gold_rows,
       count(DISTINCT order_date, customer_id) AS distinct_keys
FROM gold_daily_customer_revenue;
-- 35000 | 35000   (equal = the declared grain holds)
    -- Cell 7 (SQL): reconcile Gold against the source
SELECT (SELECT sum(orders)      FROM gold_daily_customer_revenue)          AS gold_orders,
       (SELECT count(*)         FROM silver_orders WHERE amount IS NOT NULL) AS silver_valid_rows,
       (SELECT sum(revenue_brl) FROM gold_daily_customer_revenue)          AS gold_revenue,
       (SELECT sum(amount)      FROM silver_orders)                        AS silver_revenue;
-- 199800 | 199800 | 21958100.00 | 21958100.00
    -- Cell 8 (SQL): the constraint in action. EXPECTED TO FAIL.
INSERT INTO gold_daily_customer_revenue VALUES (DATE'2026-11-16', 'c_9999', 1, -5.00);
-- error: CHECK constraint revenue_non_negative (revenue_brl >= 0) violated. The whole insert is rejected.

# Cell 10 (Python): the quality_gate task, as it would run inside the Job
q = spark.sql("""
  SELECT count(*) AS total, count(*) - count(amount) AS bad
  FROM workspace.dd_w46_db.silver_orders""").first()
g = spark.sql("""
  SELECT count(*) AS n, count(DISTINCT order_date, customer_id) AS k, sum(orders) AS o
  FROM workspace.dd_w46_db.gold_daily_customer_revenue""").first()

null_pct = 100.0 * q.bad / q.total
grain_ok = g.n == g.k
recon_ok = g.o == q.total - q.bad
gate = "pass" if (null_pct <= 0.5 and grain_ok and recon_ok) else "fail"
print(f"null_pct={null_pct:.2f} grain_ok={grain_ok} recon_ok={recon_ok} gate={gate}")

    Skew: see the hot key, then salt it

    %python
# Cell 11 (Python): how lopsided is customer_id?
from pyspark.sql import functions as F
s = spark.table("workspace.dd_w46_db.silver_orders").where("amount IS NOT NULL")
s.groupBy("customer_id").count().orderBy(F.desc("count")).show(3)
# c_0000 | 120000   <- about 60% of 199,800 valid rows
# then customers with 16 rows each (ties, so which ones appear varies)
    %python
# Cell 12 (Python): naive vs salted groupBy(customer_id), same answer
SALT = 8
naive = (s.groupBy("customer_id")
          .agg(F.count("*").alias("orders"),
               F.sum("amount").cast("decimal(18,2)").alias("revenue_brl")))

partial = (s.withColumn("salt", F.pmod(F.hash("order_id"), F.lit(SALT)))   # deterministic salt
            .groupBy("customer_id", "salt")                                  # stage 1: hot key split 8 ways
            .agg(F.count("*").alias("orders"), F.sum("amount").alias("revenue_brl")))
salted = (partial.groupBy("customer_id")                                     # stage 2: combine partials
            .agg(F.sum("orders").alias("orders"),
                 F.sum("revenue_brl").cast("decimal(18,2)").alias("revenue_brl")))

partial.where("customer_id = 'c_0000'").orderBy("salt").show()
# 8 rows (salt 0..7), roughly 15,000 orders each, summing to 120000
print(naive.count(), salted.count())                                         # 5000 5000
print(naive.exceptAll(salted).count(), salted.exceptAll(naive).count())      # 0 0
salted.where("customer_id = 'c_0000'").show()
# c_0000 | 120000 | 12960000.00

    Checklist (saved)

    6 · Interview questions · ~8 min

    "Build it gated, orchestrate it, debug it from evidence." Say it out loud, then reveal.

    Four questions on diagnosing a slow job and choosing a trigger, plus one on the gate. Answer in about 90 seconds each, as you would in a senior DE loop, then compare.

    Q1. A daily Gold job that took 6 minutes now takes 45, and nobody changed the code. Walk me through how you find the cause.

    Strong answer: I start with evidence, not knobs. 1) Run history: the job's matrix view gives me the baseline, when the jump started and whether it's every run or occasional. A green check isn't "fine" if it's 8× the baseline. 2) Task level: the task DAG and per-task durations show which task grew. If the upstream Silver task is flat, input volume didn't explode and one step changed behaviour. 3) Inside the task: on classic compute I open the Spark UI, go to the longest stage and compare task metrics. Max duration and max shuffle read far above the median or 75th percentile means skew. Spill shows in that stage's details, not in the job total. If every task got slower evenly, it's growth or I/O, not skew. On serverless I use the query profile from the run's timeline instead. 4) Correlate with what changed in the data: here a new reseller with 60% of the orders, so GROUP BY customer_id sends 60% of the rows to one task. 5) Fix and record: I pick the fix that matches the cause, measure it, and log change, metric before, metric after and data volume, so the next person has a baseline and doesn't start from "add nodes".

    Q2. The Spark UI shows one task running for 36 minutes in a groupBy("customer_id") stage. A teammate says "turn on AQE and add executors". What do you say?

    Strong answer: Neither one addresses the cause. AQE is already on by default on Databricks, and its skew handling splits skewed partitions of sort-merge and shuffle hash joins. It doesn't split a skewed aggregation. More executors don't help either: every row for the hot key hashes to the same partition, so that one task still runs on one core while the new cores sit idle. Raising spark.sql.shuffle.partitions fails for the same reason. The fix is to salt the key: add a salt column (I prefer a deterministic one like pmod(hash(order_id), N) so reruns behave the same), aggregate by (customer_id, salt), then aggregate the partials by customer_id. Sums and counts combine exactly. For distinct counts I'd be careful, because distincts don't add across buckets. This is the exam guide's sample question 1, and the answer there is D, salting. If the same skew showed up in a join, I'd first check whether AQE's skew-join split kicked in (it only does above its size thresholds, and never for broadcast joins) before salting.

    Q3. How do you choose between a schedule, a file arrival trigger and a table update trigger for a Gold job?

    Strong answer: I match the trigger to how the data arrives and to the SLA. Schedule if the upstream lands on a reliable clock or the business wants the table refreshed at a fixed time. It's simple, but it either waits too long or runs before the data is there. File arrival if the upstream is a file drop into a Unity Catalog volume or external location and nothing writes a table yet. It checks for new files about every minute (best effort), only new files count, and I'd usually pair it with Auto Loader so each file is processed exactly once. Table update if another team's job writes a UC table at irregular times. I run when their commit lands without knowing anything about their process, and I can trigger on any or all of several tables. For both event triggers I'd set wait after last change so a burst of commits becomes one run, and minimum time between triggers to cap the run rate. I'd also make sure the job's Run as identity has SELECT on the monitored tables, or the trigger can't evaluate. Whichever I pick, the tasks must be idempotent, because event triggers and retries mean the same data can be processed twice.

    Q4. The job failed in task 3 of 5 at 06:10. The SLA is 07:00. What do you do, and what could go wrong?

    Strong answer: First I make sure consumers are protected: because the gate and publish come after the failed task, they were marked Upstream failed, and finance still sees yesterday's correct table. Then I read the failed task's error and output on the task run page. If the cause is transient, the retry policy may already have handled it. If it's code or data, I fix it, then use Repair run instead of a full rerun. Repair re-runs only the unsuccessful tasks and their dependents, so the two upstream tasks that succeeded don't run again, and repaired tasks pick up the current code and settings. I can override parameters in the repair dialog if needed. The catch is that Jobs doesn't make tasks idempotent. If task 3 appended half its output before failing, a repair can duplicate it. That's why the build uses INSERT OVERWRITE / replaceWhere or MERGE, never a plain append. Afterwards the run's duration includes the original attempt plus the repair, so I add a note to the tuning log so it doesn't skew the baseline.

    Q5. Where do you put data quality checks for a Gold revenue table, and what happens to the bad rows?

    Strong answer: In layers, because each one catches something different. Silver: try_cast turns bad strings into NULLs instead of failing the job (serverless runs in ANSI mode, so a plain cast fails), and I count those NULLs as a metric. Rows I can't use go to a quarantine table with a reason, so they can be reviewed and replayed rather than silently lost. Gold table: NOT NULL on the grain columns and a CHECK like revenue_brl >= 0. A violating write fails the whole transaction, so nothing partial lands. Gate task: aggregate checks that no row-level rule can see. Is the grain unique (count(*) = count(DISTINCT keys))? Does Σ orders in Gold equal the valid Silver rows? Is the null rate under the threshold? The result goes out as a task value, and an if/else task decides publish vs hold. If this were a Declarative Pipeline, row rules would be expectations: warn writes the bad rows and records metrics, drop removes and counts them, and fail stops the update. Since none of them keeps the bad rows, I'd still add a quarantine pattern next to them.
