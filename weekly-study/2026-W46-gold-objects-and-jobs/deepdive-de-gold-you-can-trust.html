    A Gold table is a product with a promise

    This week's DE pills (DE1–DE4) looked like four separate topics. They are really three parts of one promise to the people who read a Gold table, plus a second tool that can do the same job. Each card is one pill reduced to the rule worth keeping.

    DE2 · Boundaries, contracts, idempotent Gold

    Correct: the table says what one row means, and re-running a day can't change the answer.

    • Bronze keeps raw data, Silver cleans and conforms it, Gold holds the business logic and the grain consumers rely on.
    • Contracts are made of schema enforcement, expectations, NOT NULL / CHECK constraints and informational PK/FK.
    • Drop bad rows in Silver. Stop the run in Gold.
    • INSERT INTO … REPLACE WHERE with a run_date parameter, MERGE on business keys, or a materialized view.
    DE1 · Skew and file layout

    Fast: the layout still works on Black Friday and in three years' time.

    • Skew shows up in the Spark UI as a few tasks that run far longer than the median.
    • Layered fixes: AQE skew join, broadcasting small dims, salting.
    • Hive-style partitioning on a skewed or high-cardinality key gives you one giant partition and lots of tiny files.
    • Liquid clustering (CLUSTER BY, CLUSTER BY AUTO) plus OPTIMIZE in the Job.
    DE4 · Observability and SLAs

    Watched: you find out before finance does.

    • Tests check what you predicted could break. Observability catches what you didn't predict.
    • The five pillars are freshness, volume, schema, distribution and lineage.
    • SLI = what you measure, SLO = your internal target, SLA = the promise to the consumer.
    • UC data quality monitoring, SQL alerts, Jobs duration warnings, and system.access.table_lineage to see the blast radius.
    DE3 · dbt (sidebar)

    The same promise, written in a different tool.

    • Models plus ref() give you the DAG. Materializations are table, view, incremental and materialized_view.
    • Incremental strategies (merge, replace_where, microbatch) are the idempotent Gold patterns.
    • Tests and model contracts play the role of expectations and constraints.
    • dbt runs as a task inside a Lakeflow Job.
    What's out of scope today. Silver is assumed clean. SCD2 and AUTO CDC were covered in W44, so here we only use the SCD2 customer dimension. Testing pipelines as code is next week (W47), so tests get only a light touch.
    Tie-in with Gerald's DB pills this week: DB1 tuning knobs → step 3 (fast). DB2 re-runnable Bronze → Gold and DB3 Gold objects → step 2 (idempotent build, MV vs table vs view). DB4 data quality → step 1 (contract) and the quality gate in step 4.

    Declare the contract before you write the SELECT

    Finance doesn't care how the table is built. They care what one row means and whether the numbers are right at 7 AM. Write that down first, then turn as much of it as possible into something the platform enforces or checks.

    Gold tableGrain (one row per…)KeyBuilt from
    gold.fact_daily_revenuesale_date × store × product(sale_date, store_id, product_id)orders ⋈ order_items, COMPLETE orders only
    gold.revenue_by_segmentsale_date × customer segment(sale_date, segment)orders ⋈ items ⋈ dim_customer (SCD2, point-in-time)

  sale_date   DATE          NOT NULL,
  store_id    STRING        NOT NULL,
  product_id  STRING        NOT NULL,
  units       BIGINT,

    What each piece actually does

    MechanismEnforced?What happens on a violation
    Schema enforcement (Delta)YesA write with mismatched columns/types is rejected (unless you enable schema evolution).
    NOT NULL / CHECK (Delta constraints)YesThe whole write transaction fails. Nothing partial lands.
    PRIMARY KEY … RELY (UC informational)NoDuplicates are accepted. RELY tells the optimizer it may trust the key for rewrites, so a key that's lying can give wrong query results. That's why you still need a duplicate check (the quality gate).
    LDP expectationsYour choiceexpect = keep and record, expect_or_drop = drop the row, expect_or_fail = fail the update. In SQL: CONSTRAINT c EXPECT (…) ON VIOLATION DROP ROW | FAIL UPDATE.
    The SLA is part of the contract too: "fresh by 7:00 AM ET, complete within ±2% of the 7-day average, no duplicate grain rows." Each clause becomes an SLI you can measure (step 5). If you can't measure a clause, you can't promise it.

    Exercise: drop in Silver, or fail in Gold?

    Rule of thumb from DE2: bad rows are a Silver problem (drop or quarantine and count them). A bad table is a Gold problem (stop before you publish). Pick an action for each case.

    4 · Walkthrough step 2 of 6 · ~7 min

    Re-runs are safe by design

    At 05:10 the build task times out halfway through, the retry runs, and finance sees revenue doubled for yesterday. If a daily Gold load is a plain append, every retry, repair run or backfill makes this bug possible.

    The bug: plain append 
    INSERT INTO gold.fact_daily_revenue
SELECT … WHERE o.order_date = :run_date;
-- run twice → every row for that
-- day exists twice → revenue x2

    The hands-on uses the toy data: 2026-11-12 revenue goes from 125.00 to 250.00.

    The fix: REPLACE WHERE 
    INSERT INTO gold.fact_daily_revenue
REPLACE WHERE sale_date = :run_date
SELECT … WHERE o.order_date = :run_date;
-- atomic: delete that day + insert
-- in one Delta commit

    Run it once or five times and you get the same result: 125.00.

    Details that matter (from the Delta selective-overwrite docs):
    • The predicate is an arbitrary expression over the table's columns. The table doesn't need to be partitioned on it, so it works on a liquid-clustered table.
    • By default, if the SELECT produces a row that doesn't match the predicate, the write fails. That's a useful safety net: a missing WHERE in the SELECT can't overwrite other days.
    • If the SELECT returns zero rows, REPLACE WHERE still deletes the matching data. An empty Silver day wipes the Gold day, which is one more reason for a volume gate before publish (step 4).
    • SQL needs DBR 12.2 LTS or above. The Python equivalent is .mode("overwrite").option("replaceWhere", "sale_date = '…'").
    • run_date comes from the Job (step 4). In a notebook task, job parameters arrive as widgets, and SQL cells reference them as :run_date. A backfill is just a re-run with another date.

    Decision: pick one for each table

    Late data, in one line: REPLACE WHERE for the daily slice, plus either a short lookback (sale_date BETWEEN date_sub(:run_date, 3) AND :run_date) or a targeted backfill run when a late batch lands. Use MERGE when corrections are scattered and key-level.
    5 · Walkthrough step 3 of 6 · ~6 min

    Black Friday: 20 minutes becomes 3 hours

    The old table was PARTITIONED BY (store_id), and the build did repartition("store_id") before writing so that each task wrote one store's folder. On Black Friday the flagship store S1 has 40% of the rows. One task now writes 40% of the day while 799 others sit idle.

    1 · Spot it (don't guess)

    • Spark UI → the slow stage → Summary metrics for tasks: the median task takes seconds and the max takes most of the stage. Shuffle read size per task shows the same skew.
    • Compare with the input size: if every task got slower, the problem is growth, not skew. If one task got slower, it's skew.
    • Look for small-file symptoms too: hundreds of tiny files per store partition and slow listing/scans.

    2 · Fix it in layers (cheapest first)

    LayerWhat it doesHelps here?
    AQE skew join (spark.sql.adaptive.skewJoin.enabled, on by default)Splits oversized partitions of a sort-merge join into smaller tasks at runtime.Only for skewed joins. It doesn't touch a skewed repartition before a write.
    Broadcast the dims (/*+ BROADCAST(p) */, or rely on the auto threshold)Sends dim_product / dim_customer to every executor, so there's no shuffle on the fact side.Yes for the joins. Dims are small.
    SaltingAdds a random suffix to the hot key, works on the pieces, then combines them.A last resort for skewed joins or aggregations that AQE can't split. Adds complexity.
    Layout changeStop shuffling by store to write folders. Use liquid clustering on (sale_date, store_id).Yes, this is the root cause.

    3 · The layout fix

    -- new table: cluster, don't partition (liquid clustering is not compatible with PARTITIONED BY or ZORDER)
CREATE TABLE gold.fact_daily_revenue (…) CLUSTER BY (sale_date, store_id);

-- existing partitioned table: convert in place (docs: "Use liquid clustering for tables")
ALTER TABLE gold.fact_daily_revenue REPLACE PARTITIONED BY WITH CLUSTER BY (sale_date, store_id);
OPTIMIZE gold.fact_daily_revenue;          -- incremental: clusters data written since the last OPTIMIZE

-- query patterns keep changing? let Databricks choose the keys (uses predictive optimization)
ALTER TABLE gold.fact_daily_revenue CLUSTER BY AUTO;
    • Clustering groups data by key ranges into files of a sensible size, so S1's Black Friday rows simply take more files instead of one giant folder and one giant task.
    • You can use up to four clustering keys. Keys can be changed later without rewriting existing data. After changing them, run OPTIMIZE (or OPTIMIZE FULL to recluster everything).
    • Finance queries filter by date range and store, so (sale_date, store_id) gives data skipping on both. Don't add product_id just in case: on smaller tables, more keys can make single-column filters slower.
    • Make OPTIMIZE a Job task after the build and before publish (step 4). With predictive optimization enabled, Databricks can also run it for you.

    The Lakeflow Job is where the promise gets wired together

    Steps 1–3 are code. The Job turns them into a promise kept every day: it orders the work, passes the date, retries transient failures, blocks bad data from reaching finance, and warns you while there's still time.

    {
  "name": "gold_daily_revenue",
  "parameters": [ { "name": "run_date", "default": "{{job.start_time.iso_date}}" } ],
  "schedule": { "quartz_cron_expression": "0 0 5 * * ?", "timezone_id": "America/New_York" },
  "health": { "rules": [ { "metric": "RUN_DURATION_SECONDS", "op": "GREATER_THAN", "value": 3600 } ] },
  "email_notifications": {
    "on_failure": ["data-oncall@example.com"],
    "on_duration_warning_threshold_exceeded": ["data-oncall@example.com"]
  },
  "tasks": [
    { "task_key": "silver_refresh", "max_retries": 2, "min_retry_interval_millis": 300000, "...": "..." },
    { "task_key": "build_gold",   "depends_on": [ { "task_key": "silver_refresh" } ], "max_retries": 2, "...": "..." },
    { "task_key": "quality_gate", "depends_on": [ { "task_key": "build_gold" } ],   "max_retries": 0, "...": "..." },
    { "task_key": "optimize",     "depends_on": [ { "task_key": "quality_gate" } ], "...": "..." },
    { "task_key": "publish",      "depends_on": [ { "task_key": "optimize" } ],     "...": "..." }
  ]
}
    • Retries are only safe because step 2 is idempotent. Retrying a plain append is exactly how revenue doubles.
    • The quality gate has no retries. Duplicate or missing data won't fix itself on a second try. Failing stops publish, so finance keeps yesterday's correct table instead of today's wrong one.
    • The duration warning is the SLA alarm. With a 05:00 start and a 07:00 deadline, a warning at 60 minutes leaves about an hour to react. A failure notification alone may come too late.
    • run_date is a job parameter. {{job.start_time.iso_date}} is the run's start date in UTC. If the run builds yesterday, subtract a day in the SQL. To backfill, use "Run now with different parameters" and pass another date. The code doesn't change.

    Know before finance does

    The quality gate catches what you predicted (duplicates, a volume drop). Monitoring catches what you didn't: a table that silently stopped updating, or a slow drift. Lineage tells you who to call.

    SLA clauseSLI (what you measure)How on DatabricksFires…
    Fresh by 07:00 ETTime of the last successful commit to GoldUC data quality monitoring, anomaly detection (freshness: learns the commit pattern and flags a table as stale when a commit is unusually late). Jobs duration warning.Before 07:00
    Complete within ±2%Rows and revenue for run_date vs the 7-day averageAnomaly detection (completeness: flags rows in the last 24 h below the predicted range). A Databricks SQL alert with your exact ±2% rule. The quality_gate task.In the run, and again at 06:30
    No duplicate grainCount of keys with count(*) > 1quality_gate (fails the run)In the run
    Distribution looks normalNull %, revenue percentiles, driftData profiling (formerly Lakehouse Monitoring) on the Gold tableOn each refresh
    -- SQL alert query: % deviation of the latest day vs the previous 7 days (trigger when abs_dev > 0.02)
WITH d AS (
  SELECT sale_date, SUM(revenue) AS rev
  FROM gold.fact_daily_revenue
  WHERE sale_date >= current_date() - INTERVAL 8 DAYS
  GROUP BY sale_date
)
SELECT abs(l.rev - avg(p.rev)) / avg(p.rev) AS abs_dev
FROM (SELECT * FROM d ORDER BY sale_date DESC LIMIT 1) l
JOIN d p ON p.sale_date < l.sale_date
GROUP BY l.rev;
    ±2% on revenue is strict. Normal weekday/weekend swings may be bigger than that. In real life you'd compare against the same weekday, or agree on the threshold with finance. That's an SLO conversation, not a code problem.

    Lots of US job posts ask for "dbt + Databricks" or "dbt + Snowflake". The patterns carry over one to one. Only the syntax changes.

    • Orchestration: a dbt task inside the same Lakeflow Job (e.g. dbt build --select fct_daily_revenue --vars '{run_date: "2026-11-12"}'), followed by the same quality gate and publish tasks.

    Cell 2 · The contract as DDL

    CREATE OR REPLACE TABLE fact_daily_revenue (
  sale_date DATE NOT NULL, store_id STRING NOT NULL, product_id STRING NOT NULL,
  units BIGINT, revenue DECIMAL(18,2), order_count BIGINT,
  CONSTRAINT fact_daily_revenue_pk PRIMARY KEY (sale_date, store_id, product_id) RELY
) CLUSTER BY (sale_date, store_id);

SELECT o.order_date AS sale_date, o.store_id, i.product_id,
       SUM(i.qty) AS units,
       CAST(SUM(i.qty * i.unit_price) AS DECIMAL(18,2)) AS revenue,
       COUNT(DISTINCT o.order_id) AS order_count
FROM silver_orders o
JOIN silver_order_items i ON o.order_id = i.order_id
WHERE o.status = 'COMPLETE'
GROUP BY ALL;

    Cell 8 · Second Gold table: revenue by segment (point-in-time SCD2 join)

    CREATE OR REPLACE VIEW revenue_by_segment_v AS

    Checklist

    10 · US senior DE interviews · ~5 min

    Say it out loud, then open the strong answer

    Answer each question out loud in about 90 seconds before you click. Strong senior answers start with the consumer and the contract, and only then get to tools.

    Q1 (system design). "Design the daily revenue Gold layer for finance with a 7 AM SLA. How do you make sure it's correct, on time, and that you know before finance does when it isn't?"
    1. Contract first. State the grain (date × store × product), the keys, NOT NULL/CHECK constraints, and the SLA in measurable terms: fresh by 7, ±X% completeness, zero duplicate keys.
    2. Correct. Partition-scoped, idempotent writes: REPLACE WHERE sale_date = :run_date for the daily slice, MERGE for scattered late corrections, an MV for the small aggregate. Retries and backfills are then safe by design.
    3. Fast. Choose the layout from query patterns: liquid clustering on date + store, no over-partitioning, broadcast the dims, OPTIMIZE as a task.
    4. On time. A Job DAG with retries on transient tasks, a blocking quality gate before publish, and a duration warning set early enough to act before the deadline.
    5. Watched. SLIs for freshness, volume and duplicates, with alerts that fire before 7 AM. Lineage for blast radius. A runbook and a named on-call owner.
    6. Trade-offs. MV vs table (convenience vs control). Fail vs publish-with-warning (late-but-right vs on-time-but-flagged, agreed with finance). OPTIMIZE cost vs query speed.
    Q2 (debugging). "The nightly Gold job went from 20 minutes to 3 hours and missed the SLA. Walk me through it."
    1. Protect the consumer first. Tell finance, and decide with them whether to keep yesterday's table or publish partial data with a flag.
    2. Diagnose with data. Spark UI: which stage, and is the max task time far above the median (skew) or is everything slower (growth)? Check input size vs last week and small-file counts.
    3. Fix in layers. Confirm AQE skew join and broadcast of the dims → salting if a join or aggregation still has a hot key → fix the root cause in the layout (here, partition-by-store + repartition by store → liquid clustering on (sale_date, store_id) + OPTIMIZE).
    4. Prevent a repeat. A duration warning tied to the SLA, a volume monitor, a load test before the next peak, and a blameless post-mortem.
    Q3 (trade-off). "MERGE, INSERT OVERWRITE/REPLACE WHERE, or a materialized view for a Gold fact: how do you choose?"

    It depends on how the changes arrive. If they arrive as whole time slices (a day is recomputed), REPLACE WHERE is the simplest and cheapest: an atomic swap of one slice, idempotent with no key logic. If they're scattered key-level corrections or deletes across history, MERGE on the business key with a recency guard, and make sure the source has one row per key. If it's an aggregate over other governed tables and the freshness target fits a scheduled refresh, an MV lets the engine handle incremental refresh. What you give up is control of the write path and some debuggability. I'd often combine them: REPLACE WHERE for the fact, an MV for the segment rollup.

    Q4 (behavioral, tech lead). "Tell me about a time a data product missed its SLA."

    STAR: S: the daily revenue table finance uses for the morning report. T: I owned the pipeline and the fix. A: I told finance within minutes and held the stale-but-correct table, found the cause (for example a non-idempotent retry, or skew from a partition key), shipped the fix, and backfilled the affected days with parameterized re-runs. R: back within the SLA the next day. Then the part that makes it a lead answer: the standard I set for the team, which was an SLA per Gold table, idempotent writes as a code-review rule, and alerts that fire before the deadline instead of after it.
