    1 · Recap · ~4 min

    "We have 40 Postgres tables to land as SCD2 Silver"

    This week's DE pills (DE1–DE4) answer four questions about that one sentence. Is the data correct? Can we do it for 40 tables without writing 40 pipelines? How do we know a change won't break all 40 at once? How fresh does it need to be, and what does that cost? Each card is one pill reduced to the rule worth keeping. The rest of the lesson is about how they fit together.

    DE3 · CDC end to end

    Correct: order by the source's sequence (LSN), never by arrival time, and make the apply replay-safe.

    • Log-based capture (Debezium reads the Postgres WAL) sees deletes and every intermediate state. Query-based capture (updated_at > :hwm) misses hard deletes.
    • The four hard problems are ordering, duplicates (at-least-once transport), deletes/tombstones, and late events.
    • On Databricks: AUTO CDC / create_auto_cdc_flow, or MERGE with an s.lsn > t.lsn guard.
    DE4 · Metadata-driven pipelines

    Scale: write the pattern once and describe each table in config. Table #41 should be a one-file PR.

    • Config lives in YAML in Git (reviewed) or a Unity Catalog control table. A good rule: definitions in Git, runtime state (watermarks, last run) in tables.
    • Two fan-out styles: a Python loop inside a Declarative Pipeline, or a Job For each task.
    • Keep the framework thin (the 80%), with escape hatches for the 20%.
    DE2 · Testing pipelines as code

    Safe: test the code before deploy and the data at runtime. You need both.

    • Pure DataFrame functions in a module, with pytest and assertDataFrameEqual on 3–10 rows.
    • Contract/schema tests, a few integration runs in a dev workspace (bundles), and expectations in prod.
    • In a config-driven system, the config itself needs a contract test.
    DE1 · Streaming vs batch (light thread)

    Right-sized: the same code can run triggered on a schedule or continuously. Pick the cheapest mode that meets the SLA.

    • Triggered mode processes what's available and stops (the availableNow idea). Continuous mode keeps the tables fresh as data arrives.
    • A 15-minute SLA rarely justifies 24/7 compute.
    Why together: CDC is the correctness problem, metadata is how you solve it at scale, tests make it safe (a config bug breaks 40 tables at once), and streaming vs batch picks the latency and cost. It's one system, and a senior interview answer walks through all four in that order.

    3 · Walkthrough step 1 of 7 · ~5 min

    Capture from the log, land it untouched

    The scenario is a mid-size US e-commerce company with Postgres for orders, customers, products and about 37 more tables. Debezium reads the WAL and publishes one change event per row change. Our job starts where those events land.

    What one change event looks like (flattened)

    Debezium's envelope has before, after, op and source metadata. Most teams flatten it in Bronze into the row's columns plus a few control columns:

    customer_idemailcityoplsn_ingested_at
    42ana@x.comAustinc (create)10009:00:03
    42ana@x.comDenveru (update)20009:00:04
    42nullnulld (delete, key from before)40009:00:05

    op = 'r' marks rows read during Debezium's initial snapshot. lsn is the Postgres log position, which is the source's own order of events. _ingested_at is when we received it, so it's useful for freshness and debugging but useless for ordering.

    The four hard problems, and where this system solves each one

    Problem (DE3)Where it's handled here
    Ordering: Kafka orders only within a partition, and files and retries reorder eventsSilver: sequence_by = lsn in create_auto_cdc_flow. Validated in the config contract test.
    Duplicates: transport is at-least-onceSilver: AUTO CDC is idempotent on keys + sequence_by. Bronze stays append-only and keeps them, which is fine because Bronze is the replay log.
    Deletes: op='d', then a Kafka tombstone (null value)Bronze drops null-value tombstones (they carry no row). Silver uses apply_as_deletes = "op = 'd'". In SCD2 the current version gets closed instead of erased.
    Late events: an older change arrives after a newer oneSilver: sequencing puts it in the right slot in history. AUTO CDC keeps delete tombstones for a while (default two days, set with pipelines.cdc.tombstoneGCThresholdInSeconds) so a late update can't bring a deleted row back.

    Bronze: append-only, with cheap structural expectations

    Why drop here and not fail? A row with a null key or a null LSN can't be applied correctly anyway, so dropping it keeps the other 39 tables flowing. The drop counts show up in the pipeline event log (flow_progress.data_quality), and that's where you alert (Gerald's DB2). If a whole table starts dropping, that's an incident, not a data-quality metric.

    One YAML entry per table, validated like code

    Forty tables share one shape: a key, an LSN, an op code, SCD1 or SCD2. That's exactly when a metadata-driven pipeline pays off (DE4). The config becomes the most important file in the repo, because one bad line now affects the whole pipeline.

    Where the config lives
    • YAML in Git: reviewed, versioned, deployed with the bundle. The best home for definitions.
    • UC control table: queryable and editable without a deploy, but it needs its own change control. The best home for runtime state (watermarks, last success).
    Contract test on the config (CI)
    • Every entry has name, a non-empty keys, and a scd_type of 1 or 2.
    • Keys and sequence_by exist in the source schema.
    • sequence_by is on an allow-list of monotonic columns (lsn, or struct(ts, lsn)).
    • No entry was removed without an explicit retired: true (step 3 explains why).
    Fan-out: loop or For each?
    • Loop inside the pipeline: same-shaped tables, one dependency graph, lineage and expectations for free. Our Silver layer.
    • Job For each: heterogeneous sources, per-item retries, a concurrency cap. Our Gold models.

    The heart of it: a factory function per config entry

    This is where CDC (DE3), metadata (DE4) and Gerald's AUTO CDC (DB3) become one file. The pipeline reads the config once, then calls build(entry) for each table.

    from pyspark import pipelines as dp
from pyspark.sql import functions as F

def build(e):                                   # factory: every value is a parameter
    name, keys, seq = e["name"], list(e["keys"]), e["sequence_by"]

    @dp.table(name=f"bronze_{name}")
    @dp.expect_all_or_drop({"key_not_null": " AND ".join(f"{k} IS NOT NULL" for k in keys),
                            "valid_op": "op IN ('c','u','d','r')",
                            "seq_not_null": f"{seq} IS NOT NULL"})
    def bronze():
        return spark.readStream.table(e["raw_table"])

    dp.create_streaming_table(name=f"silver_{name}",
                              comment=f"{name}: SCD{e['scd_type']} from Debezium via AUTO CDC")
    dp.create_auto_cdc_flow(
        target=f"silver_{name}",
        source=f"bronze_{name}",
        keys=keys,
        sequence_by=F.col(seq),
        apply_as_deletes=F.expr(e["delete_marker"]),
        except_column_list=list(e["exclude"]),
        stored_as_scd_type=int(e["scd_type"]),
    )

for entry in load_config():                       # outside dataset functions: OK to read files/tables here
    build(entry)

    Pipeline functions are registered lazily and evaluated during planning, so a loop variable captured by reference resolves to its final value. Both fixes come from the Databricks docs ("Create tables in a for loop" and the metaprogramming tutorial). The factory is cleaner once you have more than one dataset per entry.

    Gotcha 2: the list must be additive

    The docs warn that if a dataset defined in an earlier run is missing from a later run, the pipeline drops it from the target schema automatically. In a config-driven pipeline, deleting a YAML entry (or a config read that silently returns an empty list) means the Silver table disappears. That's why the contract test refuses removals without retired: true, and why load_config() should fail loudly when it finds zero entries.

    What AUTO CDC gives you (and what it asks of you)

    ConcernWhat happens
    Out-of-order eventsOrdered by sequence_by. In SCD2 the sequence values become __START_AT / __END_AT, and the current version has __END_AT = NULL.
    Replays / duplicatesDocumented as idempotent with respect to keys and sequence_by: applying the same change twice gives the same final state.
    TiesThe sequence must give "one distinct update per key at each sequencing value". If commit timestamps can tie, use sequence_by=F.struct("source_ts_ms", "lsn"). The first field is compared first and the second breaks ties.
    Deletes in SCD2The current version is closed (__END_AT = the delete's sequence). History stays.
    Track only some columnstrack_history_column_list=[...]. Changes to other columns update the current version in place (the track_history override in the YAML).
    Initial snapshotDebezium's op='r' rows flow through as upserts. For a backfill from a separate snapshot table there's a once=True flow (see the docs on replicating an RDBMS table).
    RequirementsServerless pipelines or the Pro/Advanced edition. NULL sequence values aren't supported, which is why the Bronze expectation exists.
    The hand-rolled alternative: MERGE with an LSN guard (when you're outside a pipeline) 
    MERGE INTO silver.customers AS t
USING (SELECT * FROM batch
       QUALIFY ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY lsn DESC) = 1) AS s
ON t.customer_id = s.customer_id
WHEN MATCHED AND s.lsn > t.lsn AND s.op = 'd' THEN DELETE
WHEN MATCHED AND s.lsn > t.lsn THEN UPDATE SET *
WHEN NOT MATCHED AND s.op != 'd' THEN INSERT *;

    This is SCD1 only. Once a row is hard-deleted, a late update has nothing to compare against and gets re-inserted (a "zombie row"). AUTO CDC's tombstones exist for exactly this case, and it's also why teams soft-delete when they roll their own. SCD2 written by hand is a lot more code. Say this in interviews: "I'd use the platform's CDC apply and keep MERGE for the edge cases."

    Streaming vs batch, applied (DE1)

    Triggered pipeline on a schedule

    Each update processes everything that has arrived since the last checkpoint and then stops. It's still streaming tables and still incremental, but you pay only while it runs. With a 15-minute SLA, a 10–15 minute schedule (plus monitoring the run duration) is the default answer.

    Continuous pipeline

    Always on, so latency is seconds to minutes. Worth it when the business acts on the data within minutes (fraud, inventory) or when start-up overhead makes 15-minute runs impractical. You don't rewrite the code, you change the pipeline mode. In a continuous setup, the Job's Gold fan-out usually moves to table-update triggers.

    The trade-off here is… "the code is the same. Triggered versus continuous is a deployment setting, so I'd start triggered every 10–15 minutes, measure the end-to-end lag, and only move to continuous if the SLA tightens or the run overhead eats the window."

    # src/cdc_transforms.py: pure logic, no reads or writes
from pyspark.sql import DataFrame, Window, functions as F

def latest_change_per_key(df: DataFrame, keys: list[str], seq: str = "lsn") -> DataFrame:
    """Keep one change per key: the one with the highest sequence. Exact replays collapse."""
    w = Window.partitionBy(*keys).orderBy(F.col(seq).desc())
    return df.withColumn("_rn", F.row_number().over(w)).filter("_rn = 1").drop("_rn")

    CDC again, this time inside the lakehouse

    Silver is now a CDC target. Gold shouldn't rescan 40 tables every 15 minutes, so it reads Silver's Change Data Feed: just the rows that changed. It's the same idea as Debezium, one layer later.

    # a separate Gold pipeline (or a For-each Gold task) reading Silver's changes
@dp.table(name="gold_customer_current_changes")
def gold_customer_current_changes():
    return (spark.readStream
              .option("readChangeFeed", "true")
              .table("prod.cdc.silver_customers")
              .filter("_change_type IN ('insert', 'update_postimage')")
              .filter("__END_AT IS NULL"))          # only versions that are current now
    Fact (from the docs)Why it matters here
    CDF rows carry _change_type (insert, update_preimage, update_postimage, delete), _commit_version and _commit_timestamp.Filter out the preimages unless you need "before" values.
    You can read the CDF of an AUTO CDC target like any Delta table (DBR 15.2+), as long as it's published to Unity Catalog.The SCD2 Silver tables can feed Gold incrementally.
    For SCD2 targets, the CDF primary key is keys plus coalesce(__START_AT, __END_AT), and a late event that moves __START_AT shows up as delete + insert.A late event can rewrite history rows. Gold logic has to handle deletes, not just appends.
    To stream from an AUTO CDC target you read its change feed (a documented limitation).A plain readStream of Silver isn't the pattern here.

    For simple Gold aggregates, a materialized view over silver_x WHERE __END_AT IS NULL is often simpler. The engine refreshes it incrementally when it can. Use CDF when Gold needs the change events themselves (reverse ETL, audit feeds, downstream MERGEs).

    Interview use: "Don't build your own framework if the platform already is one." dbt is a metadata-driven framework for SQL transforms. Lakeflow pipelines with AUTO CDC give you the CDC apply. Your config layer should only cover what neither gives you: which tables, keys, and SLAs.
    One honest contrast: dbt snapshots compare the table's current state each time they run, so several changes between two runs collapse into one, and hard deletes are ignored unless you set hard_deletes: invalidate (or new_record; it replaces the legacy invalidate_hard_deletes).         Pipeline · New ETL pipeline (Python), default catalog workspace, schema cdc_lab, one source file

        from pyspark import pipelines as dp
from pyspark.sql import functions as F

CONFIG_TABLE = "workspace.cdc_lab.cdc_sources"

def load_config():
    # Runs outside dataset functions, so collect() is allowed here.
    rows = [r.asDict() for r in spark.read.table(CONFIG_TABLE).collect()]
    if not rows:  # an empty config would make the pipeline drop every Silver table
        raise ValueError(f"{CONFIG_TABLE} is empty: refusing to plan")
    return rows

def build(e):  # factory function: avoids the loop-closure bug
    name, keys, seq = e["name"], list(e["keys"]), e["sequence_by"]

    @dp.table(name=f"bronze_{name}", comment=f"Raw CDC events for {name} (append-only)")
    @dp.expect_all_or_drop({
        "key_not_null": " AND ".join(f"{k} IS NOT NULL" for k in keys),
        "valid_op": "op IN ('c', 'u', 'd', 'r')",
        "seq_not_null": f"{seq} IS NOT NULL",
    })
    def bronze():
        return spark.readStream.table(e["raw_table"])

    dp.create_streaming_table(name=f"silver_{name}",
                              comment=f"{name}: SCD{e['scd_type']} via AUTO CDC")
    dp.create_auto_cdc_flow(
        target=f"silver_{name}",
        source=f"bronze_{name}",
        keys=keys,
        sequence_by=F.col(seq),
        apply_as_deletes=F.expr(e["delete_marker"]),
        except_column_list=list(e["exclude"]),
        stored_as_scd_type=int(e["scd_type"]),
    )

for entry in load_config():
    build(entry)

from pyspark.testing import assertDataFrameEqual

def latest_change_per_key(df: DataFrame, keys, seq="lsn") -> DataFrame:
    w = Window.partitionBy(*keys).orderBy(F.col(seq).desc())
    return df.withColumn("_rn", F.row_number().over(w)).filter("_rn = 1").drop("_rn")

def test_latest_wins_even_if_it_arrives_first():
    s = "customer_id INT, city STRING, op STRING, lsn BIGINT"
    ev = spark.createDataFrame([(42, "Seattle", "u", 300), (42, "Austin", "c", 100),
                                (42, "Denver", "u", 200), (42, "Denver", "u", 200)], s)
    assertDataFrameEqual(latest_change_per_key(ev, ["customer_id"]),
                         spark.createDataFrame([(42, "Seattle", "u", 300)], s))

        Five questions this system answers

        Try each one out loud first (60–90 seconds), then open the strong answer. Sunday's capstone pill takes Q1 all the way to Gold.

        Q1 (system design) · "Design ingestion of 50 OLTP tables into a lakehouse with full history, deletes, and a 15-minute freshness SLA."

        Strong answer. "I'd clarify three things first: do we need history for every table or just a few, can we read the database log, and what does '15 minutes' mean, end to end or to Silver? Assuming we can read the log, I'd use log-based CDC with Debezium or a managed connector. Query-based capture misses hard deletes and puts load on the source. Raw change events land in an append-only Bronze so we can always replay. Silver is AUTO CDC, keyed on the primary key and sequenced by the LSN, not arrival time, so duplicates and out-of-order events are harmless. I'd use SCD2 only where the business needs history and SCD1 elsewhere, because SCD2 everywhere costs storage and confuses consumers. Fifty same-shaped tables means one config-driven pipeline: a YAML entry per table with keys, SCD type and overrides, validated by a contract test in CI. For the SLA I'd run it triggered every 10–15 minutes rather than continuous, and alert on freshness and on expectation drop rates. I'd also plan the boring parts up front: a re-snapshot/backfill runbook for when the replication slot breaks, a schema-evolution policy, and a daily reconciliation of counts against the source."

        Q2 (trade-off) · "When is a metadata-driven framework a bad idea?"

        Strong answer. "When the sources don't share a shape. With eight tables that each have unique logic, config just hides if source == 'x' branches, and you've built an inner platform that's harder to debug than plain code. It's also a bad idea when nobody owns it. I'd keep it thin: standard CDC ingestion and Silver go through config, and Gold business logic stays hand-written. I'd add explicit escape hatches for odd tables, contract-test the config, and lean on platform features like AUTO CDC or dbt instead of writing my own merge engine. The success metric is that a new standard table is a one-file PR, and the failure signal is a YAML file that's started to look like a programming language."

        Q3 (testing) · "How do you test a CDC pipeline before it reaches production?"

        Strong answer. "In layers. A contract test on the config runs in milliseconds: keys exist, the sequence column is monotonic, SCD2 has a sequence, and no table disappears by accident. That one has the biggest blast radius. Unit tests with pytest and assertDataFrameEqual cover my own transforms, like envelope flattening and latest-per-key. Then an integration run: CI deploys the bundle to a dev target and runs the pipeline on fixture events I design to hurt, meaning an insert, updates, a duplicate, a late update and a delete, and asserts the exact SCD2 rows. In production, expectations on Bronze and freshness checks in the Job catch what tests can't: today's data."

        Q4 (streaming vs batch) · "Your PM asks for 'real-time' CDC. Do you go continuous?"

        Strong answer. "I'd ask what decision the data drives and how fast someone acts on it. If a dashboard is checked hourly, 'real-time' really means 'not stale', and a triggered pipeline every 10–15 minutes gives the same tables at a fraction of the cost, since compute only runs while there's work. The code doesn't change, because triggered versus continuous is a pipeline setting. So I'd ship triggered, measure end-to-end lag against the SLA, and switch to continuous only if a use case like fraud or inventory needs minutes or seconds and the cost is justified. I'd write that trade-off down so it's a decision, not a default."

        Q5 (debugging) · "A customer deleted in Postgres reappeared in Silver. What happened, and how do you fix it?"

        Strong answer. "Classic zombie row: a late or duplicate update arrived after the delete had been applied. With a hand-rolled MERGE and hard deletes there's no row left to compare the LSN against, so WHEN NOT MATCHED … INSERT brings it back. I'd confirm it from Bronze: the update's LSN is lower than the delete's, but it arrived later. Fixes, from best to least: switch to AUTO CDC, which keeps delete tombstones for a configurable window (pipelines.cdc.tombstoneGCThresholdInSeconds) longer than the maximum expected lateness; or soft-delete in Silver with an is_deleted flag and keep the LSN guard; and add a regression test with exactly that event order. Then I'd backfill the affected keys and check whether any Gold tables need a re-run."
